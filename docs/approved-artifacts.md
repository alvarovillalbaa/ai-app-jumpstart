# Approved private artifacts

With [account chat](account-chat.md) enabled, a verified user can ask the agent to save a generic plain-text note or draft. Eve's `create_artifact` tool proposes a title and exact content and always pauses for approval. The chat shows the proposed input before the owner chooses **Approve** or **Cancel**. No artifact is written before approval. A denied call has no write.

The tool verifies the current and initiating account again after the wait. The application store also requires an active, matching conversation/session binding. It records one artifact per `(operationId, callId)` with a hash of the validated input. A replay with the same input returns the immutable approved version 1, even after owner edits; changed input under the same call ID conflicts. This bounds duplicate writes across Eve retries without relying on the browser to persist the result. Artifacts remain readable by their owner after conversation revocation, but new approved creations require an active binding.

Open `/artifacts` to read saved text, download the latest version as a `.txt` file, edit it, inspect version history, delete every saved version or navigate to its source conversation. The screen fetches pages with the current account token and clears its results when the account changes. Content is rendered as text, without executing HTML. The reference action stores text in the selected application database; it does not upload files or create public download links.

Existing artifacts remain available when `AI_CHAT_ENABLED=false`, with Supabase sign-in and the application database still configured. Browser, REST, CLI and MCP keep the same owner, revision and deletion checks; no budget policy, signing key or Eve service is needed for these saved-data operations. While chat is paused, the source link opens saved activity rather than a live session. New artifacts still require enabled chat and the approved tool; disabling chat is not an erasure or cancellation operation.

The same owner-only reads are available through `GET /api/v1/artifacts?limit=20&cursor=...`, `GET /api/v1/artifacts/ARTIFACT_UUID`, CLI `npm run app -- artifacts list|get`, MCP tools `artifacts_list` and `artifacts_get`, and `artifacts:///ARTIFACT_UUID` resources. `GET /api/v1/artifacts/ARTIFACT_UUID/download` returns a private `text/plain` attachment with a UUID-based filename. `DELETE /api/v1/artifacts/ARTIFACT_UUID`, `npm run app -- artifacts delete ARTIFACT_UUID` and MCP `artifacts_delete` erase the stored artifact fields and all versions; a second deletion or a foreign owner's deletion returns 404. All saved-data paths require a current registered-user bearer token. The API has no artifact-create route: write authority comes from Eve's approved tool, not a client payload. The returned record includes the source operation/session/call IDs, title, content, `text/plain` type creation time, current `revision` and `updatedAt`; do not treat these read surfaces as public sharing.

Deletion atomically removes every saved version and replaces the artifact's title and content with fixed markers, clears its content-derived hash and removes it from list, read and download results. The original operation/call ID remain as a tombstone, so the same approved call cannot recreate it on replay. Deleting an artifact does not erase text already present in the source conversation, stream projections, external exports or database backups; those have separate retention policies.

This artifact reference does not implement uploaded-file versioning or an external side effect; separate [owner upload review](upload-review.md) supports bounded plaintext extraction. The local browser contract uses real Supabase Auth, compiled Eve and a deterministic model to check approval, denial, owner isolation, export and deletion. Hosted workflow recovery and operational replay of an in-flight tool remain separate release checks.

## Owner edits and history

`PATCH /api/v1/artifacts/ARTIFACT_UUID` accepts exactly `{"revision":1,"title":"Updated note","content":"Exact replacement text"}`. A successful save appends a complete immutable version and increments the current revision in the same database transaction. Creation is version 1. A stale revision returns 409 `artifact_conflict`; re-read the artifact and review your edit before trying again. Missing, deleted and foreign artifacts return 404. Edits do not rerun the model or change its original approved input/hash. The owner can edit an existing artifact after its source conversation is revoked. All reads, downloads and `artifacts:///UUID` resources return the latest version; an approved tool replay returns version 1.

`GET /api/v1/artifacts/ARTIFACT_UUID/versions?limit=20&before=REVISION` returns `{items,nextBefore}` newest first, with each item carrying the same artifact/source identifiers and that version's title, content, revision and update time. Omit `before` on the first page; pass `nextBefore` unchanged on the next. Pages contain at most 50 versions, and later edits cannot enter an older `before` page. Live reads are not a transaction snapshot; concurrent deletion can end an export with 404. History stays private and content renders as plain text.

CLI `artifacts update ARTIFACT_UUID patch.json` and `artifacts versions ARTIFACT_UUID --limit 20 --before REVISION` use the same authenticated API. MCP `artifacts_update` accepts `id`, `revision`, `title`, `content`; `artifacts_versions` accepts `id`, `limit`, optional `before`. These require registered account credentials; record API keys never grant artifact access. There is still no client-facing create operation.

Each artifact retains at most **100 versions**, including creation. Saving at revision 100 returns 409 `artifact_version_limit` without writing. This bounds amplification and lets SQLite, PostgreSQL, Supabase and Convex erase the entire history atomically. No-op replacements also consume a version. Title/content bounds and validation match the approved tool (120-character plain title, 32,000-character well-formed text). Deletion fences concurrent edits and tool replay, clears current content/hash, and removes history rows; source conversation/tool-result copies, exports and backups have separate retention.

Application exports now use manifest v10 and include `artifact` current snapshots plus every retained `artifact_version`; the offline verifier continues accepting v5, v6, v7, v8 and v9 exports. The export remains a sequence of owner-authorized live reads, not a full account export or database backup.

## Upgrade and rollback

SQLite adds version fields/history and backfills live artifacts under its serialized startup upgrade. PostgreSQL/Supabase apply `20260927190000_artifact_versions.sql`: version 1 copies existing live text, deleted tombstones get no history, and backend-only triggers capture edits and erase versions. Commit generated Supabase types from the migrated schema. Convex adds optional current-version fields and a private history table: existing live documents read as version 1 and materialize their original version on their first edit; deleted documents never backfill. New creations save version 1 immediately.

Deploy application readers, Eve writers and their schema together before allowing edits. Older SQLite/Convex writers do not understand immutable creation replay after edits; older browser bundles may reject the new revision fields. Do not roll back to those writers once version edits exist. Keep the forward migration and reload clients; use a compatible application rollback or restore the full database from a validated snapshot during maintenance. This release has local populated-upgrade, concurrent-edit, deletion, provider and browser proof; hosted rollout and manual recovery acceptance remain separate checks.
