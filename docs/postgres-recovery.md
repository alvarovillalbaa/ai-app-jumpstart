# Stopped PostgreSQL database set

Use this procedure when a self-hosted deployment keeps application data in PostgreSQL and Eve execution in a **different PostgreSQL database**. It makes one private, verifiable directory containing both database archives and, when selected, the matching local private upload objects. It does not collect Supabase Storage or other remote objects, cluster roles, Auth-provider data outside the application database, or a managed Vercel Workflow world.

Stop every application instance, Eve instance, Workflow worker and upload cleanup scheduler for this environment, and prevent replacement instances from restarting them. Keep them stopped through both dumps and the object copy. Let active turns settle or record them for review. Resolve any locked Graphile jobs before proceeding. `--stopped` records the operator's assertion; the command cannot discover a writer on another host or guarantee that a prior external model/tool side effect settled.

Export the intended private `DATABASE_URL` and `WORKFLOW_POSTGRES_URL` in the operator shell. This command does not load `.env.local`, and it never puts either URL in process arguments or its manifest. Use `pg_dump` and `pg_restore` from a PostgreSQL client release at least as new as the source server's major version. Choose a new path under a private backup directory, then run:

```sh
npm run backup:postgres-databases -- --create \
  --output /PRIVATE_BACKUPS/database-set-YYYYMMDD --stopped
npm run backup:postgres-databases -- --verify \
  /PRIVATE_BACKUPS/database-set-YYYYMMDD
```

For local object storage, export `UPLOAD_STORAGE_PROVIDER=local` and the intended private `UPLOAD_LOCAL_ROOT`, then add `--uploads-dir /PRIVATE_UPLOAD_ROOT` to the create command. A configured local store cannot be silently omitted, and the supplied path must match `UPLOAD_LOCAL_ROOT` when set. The command refuses a remote storage configuration with a local path. It never loads `.env.local`; supply the deployment's actual configuration deliberately.

The copy retains the backend's opaque `uploads/v1/OWNER_HASH/UPLOAD_UUID` layout under the snapshot's `uploads/` directory. All directories must be private (0700), all source files must be private (0600), and symlinks, unexpected entries and incomplete `.tmp` writes are refused. Resolve these with all writers stopped rather than treating a partial copy as a backup. The source root and destination must be separate. A set without this option records uploads as `excluded`; older version-1 manifests remain verifiable and report them as `untracked`.

For a stronger rehearsal, create two **different, empty, loopback** PostgreSQL databases and export their private URLs as `BACKUP_VERIFY_APP_DATABASE_URL` and `BACKUP_VERIFY_WORKFLOW_DATABASE_URL`. Add `--verify-restore` to the create command. It restores each archive in one transaction, compares the application migration ledger and Workflow/Graphile migration, run and event counts, and marks the manifest `restoreVerified: true` only after both database restores pass. Included objects are checked against the restored application's upload catalog. Without this flag, the same catalog check reads the stopped source database. These disposable target databases remain populated for operator inspection; drop them after the rehearsal. If either restore or catalog check fails, inspect and drop both disposable targets before retrying, even though the incomplete output directory is removed.

The catalog check pages all upload rows in a read-only repeatable-read transaction. Quarantined/clean and malware-rejected objects must exist and match their recorded size and SHA-256. Pending/deleting rows may have no object; any remaining object must match. Deleted IDs must have no bytes, and orphaned objects are refused. Integrity-rejected files may contain corrupt bytes: those private evidence files are preserved with their **actual snapshot digest**, while their rejection remains in the database. This exception does not release them or erase their recorded expected digest. The manifest contains opaque paths, sizes and digests, without filenames, raw owner identities, credentials or signing keys.

The command refuses the same source database for both roles, an existing destination, a missing stopped acknowledgement, or just one restore target. It creates the directory mode 0700, writes `application.dump`, `workflow.dump` and included objects mode 0600, then publishes version-2 `manifest.json` last with SHA-256 and size for every file. A normal failure removes the directory it created. A process crash can leave an incomplete directory: `--verify` rejects missing, extra or altered files. Re-run `--verify` after transferring a set and before recovery. Offline verification checks the captured file inventory/digests; it does not requery a database, re-run a malware scanner or certify runtime behavior. The manifest detects accidental changes but is not signed and cannot authenticate an untrusted backup. Treat the whole set as private data, including rejected files; never serve or open the backup directory as application content.

These are **two sequential database snapshots and an optional file copy**, not one distributed transaction. The stopped maintenance window prevents application/Workflow/object writes between them. The command checks for changed files during and after copying but cannot fence another host's writes. For Supabase Storage or another external object provider, use that provider's separate backup and restore procedure and record it with this excluded-object database set. Retain the matching application image digest, secrets, migration list and deployment settings in the release record.

Restore included local objects into a **new, unused** private root:

```sh
npm run backup:postgres-databases -- --restore-uploads \
  /PRIVATE_BACKUPS/database-set-YYYYMMDD --output /NEW_PRIVATE_UPLOAD_ROOT
```

This needs no database credentials. It verifies the complete set before copying, refuses an existing target or a path overlapping the snapshot, retains 0700/0600 permissions and verifies the restored hashes before reporting success. It does not restore database archives or replace a live mount. A normal copy/verification failure removes only the newly created root; an existing destination is preserved. Point `UPLOAD_LOCAL_ROOT` at it only alongside the matching restored application database. Rejected uploads remain rejected; every permitted download still needs current owner credentials and a fresh clean scan.

For recovery, verify the set, restore each archive into a fresh database with the intended roles and grants, restore any included object root, and point a disposable application/Eve deployment at the matching restored stores. Rehearse owner-isolated REST/CLI/MCP reads, a previously completed conversation, an owned follow-up, Workflow callbacks and private object references before switching traffic. The optional loopback restore uses `--no-owner --no-acl`; production roles and policies need separate review. Never overwrite an existing production database as a shortcut. `test:postgres-backup` uses PostgreSQL 18 and verifies both database restores plus actual object bytes through production HTTP handlers, foreign-owner/metadata-scope denial, fresh scanning, retained rejection and deletion/quota release. Its clean scanner is a deterministic fixture, not malware detection proof. The separate Eve runtime suite proves completed-session replay from a restored Workflow database. A combined hosted restore and a credentialed model turn remain release acceptance work.
