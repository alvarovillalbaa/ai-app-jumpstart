# Private upload foundation

Uploads are separate from approval-gated agent artifacts. `lib/uploads/validation.ts` checks actual bytes, filename and declared media type together, copies bytes before hashing, and limits one file to 5 MiB. It accepts UTF-8 `.txt`, PNG, JPEG and PDF. This is a format sanity check, **not** malware scanning or complete image/PDF parsing. `lib/uploads/contract.ts` derives an opaque object key from the verified tenant and subject plus a server-generated UUID; clients cannot choose an object path.

Self-hosted deployments may set `UPLOAD_SCANNER_PROVIDER=clamd` and an absolute `UPLOAD_CLAMD_SOCKET` path to a private ClamAV Unix socket. After quota reservation and before object storage, the server streams the validated bytes through ClamAV's `INSTREAM` protocol. An infected result returns `422`; a connection, timeout, limit or malformed-verdict failure returns `503`. Both paths leave no object and release the reservation. An incomplete scanner configuration fails closed for writes while metadata reads and deletion remain available. Keep the socket accessible only to the application and scanner, run `freshclam` to maintain signatures, set ClamAV's `StreamMaxLength` to at least 5 MiB, and run `npm run check:upload-scanner` against the live daemon before accepting uploads. The preflight sends a clean control and the harmless EICAR test bytes without writing a file. ClamAV's TCP protocol has no authentication or encryption, so this integration intentionally uses a Unix socket. See the [ClamD protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html), [signature updates](https://docs.clamav.net/manual/Usage/SignatureManagement.html) and [EICAR test file](https://www.eicar.org/download-anti-malware-testfile/).

On 2026-09-24, the preflight passed against a disposable ClamAV 1.5.4 Linux daemon with signature database 28133, using image digest `clamav/clamav@sha256:0e31ce089574268aefa0b543767d66b70240ab51ed49eec53e07f18d5629d817` and a private shared Unix-socket volume. The test container and volume were removed. This verifies the live socket exchange and two control verdicts; it does not certify detection of every threat, future signature freshness, or a production scanner deployment.

`lib/uploads/local.ts` stores private mode-`0600` files under a mode-`0700` root on a single persistent host. Its exclusive hard-link publication prevents two racing writes from replacing one another. Keep the root outside web-served directories and back it up alongside the application database. `lib/uploads/supabase.ts` uses a private, 5 MiB, octet-stream-only bucket for Vercel + Supabase. It checks the bucket before each operation and creates no public or signed URL. A live Storage test found that two concurrent `upsert: false` calls to the same key can both be acknowledged. Do not use that primitive as an atomic claim: only the catalog winner may write the object.

`lib/uploads/catalog-contract.ts` defines owner-scoped metadata and an atomic quota reservation. SQLite, PostgreSQL, Supabase PostgREST and Convex adapters pass the same concurrency, isolation and deletion contract. The default quota is 20 active files and 50 MiB per owner, including pending, quarantined and deleting files; bytes are released only after object removal is confirmed. Deleted IDs remain tombstoned. `lib/uploads/intake.ts` validates bytes, reserves one new ID, writes the object and moves metadata to **quarantined**. If a write fails after storing bytes, it attempts deletion; failed cleanup remains in `deleting` with quota held for a later retry. No transition to downloadable content exists yet.

For Supabase, apply the canonical migrations after Storage is installed. `20260924152111_private_upload_storage_policy.sql` adds a restrictive policy on `storage.objects`, so even a broad permissive policy cannot grant browser roles access to the quarantine bucket. Supabase already owns and enables RLS on that table; the migration must not alter the managed table. Plain PostgreSQL skips the Storage-specific policy. If Storage is installed after migrations were applied, apply the policy before provisioning the bucket. With operator-only `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY`, run `npm run check:upload-storage` to verify the policy and bucket; add `-- --create` to create only a missing bucket. The command refuses an existing public or misconfigured bucket. The backend secret bypasses Storage RLS, so the application must still derive every object key from a verified owner. See [Supabase private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

`npm run test:providers` checks the catalog on disposable PostgreSQL/PostgREST/Convex backends. `npm run test:upload-storage:live` additionally needs `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_ANON_KEY` and `DATABASE_URL` for a migrated, Storage-enabled **disposable** Supabase project with the private bucket provisioned. It exercises the real Storage API, anonymous denial and the composite one-writer quota race, and removes its objects. The usual `db:local:start` command excludes Storage; start a local stack with Storage enabled for this optional test. A local Storage/API/catalog run passed on 2026-09-24; hosted Storage remains unverified.

The opt-in quarantine API accepts uncompressed `application/octet-stream` requests at `POST /api/v1/uploads` with URI-encoded `x-upload-name` and `x-upload-media-type` headers. It streams at most 4 MiB, leaving room under [Vercel's 4.5 MB Function request limit](https://vercel.com/docs/functions/limitations). `GET /api/v1/uploads` returns active metadata and usage; `GET` and `DELETE /api/v1/uploads/{id}` inspect or remove an owned upload. No HTTP route returns file bytes. Registered Supabase users get upload read/write scopes; API keys can be issued `uploads:read` and `uploads:write` separately. `npm run app -- uploads put FILE`, `list`, `get ID` and `delete ID` use the same authenticated API. MCP exposes metadata listing, usage, get, delete and an owner-scoped metadata resource; it has no binary upload or download tool.

Set `UPLOAD_STORAGE_PROVIDER=local` with a private persistent `UPLOAD_LOCAL_ROOT` for a self-hosted Node service, or `UPLOAD_STORAGE_PROVIDER=supabase` with server-only Supabase credentials for Vercel or another distributed host. Local storage refuses Vercel/Lambda. Metadata is still inspectable if the object backend is temporarily unconfigured, but writes/deletes fail closed. Apply all migrations; the additive upload-list function is required for PostgreSQL and Supabase. When a storage provider is configured, `/uploads` appears in the workspace. Signed-in Supabase users use their current account session; API-key users enter an upload-scoped key that stays in tab memory. The browser shows progress, server errors and quota usage, permits refresh/retry and owner deletion, and labels every stored file as quarantined. After a network failure, timeout or cancellation, refresh before retrying because the server might already have accepted the file. The browser, API and CLI store uploads in **quarantine only**, including files that passed the optional scanner. The real-Auth browser suite checks two signed-in users, account switching, cross-owner REST and MCP denial, owner MCP metadata access without bytes, and owner deletion against local private storage. There is no safe extraction, clean/rejected catalog state, release policy or authorized download link. Do not attach quarantined bytes to Eve or serve them to a browser. A production path still needs a scanner deployment for managed hosts, quarantine release policy, cleanup/recovery worker, short-lived owner-authorized downloads and deletion of derived data. Hosted Storage and signed-in upload behavior on other data/object providers remain unverified.
