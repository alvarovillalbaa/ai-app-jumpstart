# Private upload foundation

The upload core is separate from the approval-gated artifact table. `lib/uploads/contract.ts` derives an opaque object key from the verified tenant and subject plus a server-generated UUID; a caller cannot choose a filesystem path. `lib/uploads/validation.ts` checks the real bytes, claimed media type and filename together, limits one file to 5 MiB, and copies the bytes before hashing them. The initial accepted classes are UTF-8 `.txt`, PNG, JPEG and PDF. HTML/SVG masquerading as text, malformed UTF-8, path-like names and mismatched signatures fail before storage. This is a format sanity check, **not** malware scanning or complete image/PDF parsing.

`lib/uploads/local.ts` provides private, immutable, owner-scoped storage for a single persistent host. It refuses a symlinked or group/world-accessible root, creates owner directories with mode `0700`, writes mode `0600` files, and publishes each object with an exclusive hard link after the temporary file is synced. Competing writes to one ID cannot replace a published object. Deleting or reading under another owner derives a different key. Keep the configured root on a persistent local volume, outside web-served directories, and back it up separately from the application database.

`lib/uploads/supabase.ts` adds the managed private-bucket adapter for Vercel + Supabase. It checks the bucket before every operation, uses the same owner-derived key, uploads as `application/octet-stream` without upsert, and does not generate public or signed URLs. Apply the canonical SQL migrations to the Supabase project **after Storage has been installed**: `20260924152111_private_upload_storage_policy.sql` adds a restrictive policy to `storage.objects` that denies client roles this bucket even if another permissive policy covers other files. The migration intentionally skips the Storage-specific policy on plain PostgreSQL. If Storage is added after migrations ran, apply that policy before using the bucket. The disposable Supabase-provider test models Storage RLS with a deliberately broad policy and verifies the private bucket stays inaccessible to anonymous and authenticated roles. This is SQL-policy evidence, not a live Storage API test.

For a managed project, run `npm run check:upload-storage` with operator-only `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY`. It verifies the actual SQL policy and checks that the bucket is private, limited to 5 MiB, and accepts only `application/octet-stream`. Use `npm run check:upload-storage -- --create` once to create it if absent; the command checks the SQL policy first and refuses to modify an existing public or misconfigured bucket. Keep the secret out of browser code. [Supabase's private-bucket guide](https://supabase.com/docs/guides/storage/buckets/fundamentals) explains bucket visibility; its [Storage access-control guide](https://supabase.com/docs/guides/storage/security/access-control) explains why a backend secret bypasses RLS, so application owner checks remain necessary.

This foundation is **not an enabled upload feature**. There is no browser button, HTTP endpoint, account quota, metadata row, scanner or download link yet. Do not attach these bytes to Eve or serve them to a browser until the remaining lifecycle exists. The next implementation must add durable owner-scoped metadata and quota reservation across all four application databases, quarantine/scan state, authenticated download and deletion, and cross-owner browser/provider tests. Binary content needs an explicit scanning policy before release. The Supabase adapter has contract and policy tests, but a credentialed live Storage API run remains outstanding.
