# Private upload foundation

Uploads are separate from approval-gated agent artifacts. `lib/uploads/validation.ts` checks actual bytes, filename and declared media type together, copies bytes before hashing, and limits one file to 5 MiB. It accepts UTF-8 `.txt`, PNG, JPEG and PDF. This is a format sanity check, **not** malware scanning or complete image/PDF parsing. `lib/uploads/contract.ts` derives an opaque object key from the verified tenant and subject plus a server-generated UUID; clients cannot choose an object path.

Self-hosted deployments may set `UPLOAD_SCANNER_PROVIDER=clamd` and an absolute `UPLOAD_CLAMD_SOCKET` path to a private ClamAV Unix socket. After quota reservation and before object storage, the server streams the validated bytes through ClamAV's `INSTREAM` protocol. An infected result returns `422`; a connection, timeout, limit or malformed-verdict failure returns `503`. Both paths leave no object and release the reservation. An incomplete scanner configuration fails closed for writes while metadata reads and deletion remain available. Keep the socket accessible only to the application and scanner, run `freshclam` to maintain signatures, set ClamAV's `StreamMaxLength` to at least 5 MiB, and run `npm run check:upload-scanner` against the live daemon before accepting uploads. The preflight sends a clean control and the harmless EICAR test bytes without writing a file. ClamAV's TCP protocol has no authentication or encryption, so this integration intentionally uses a Unix socket. Distributed hosts may instead use an [authenticated HTTPS scanner](remote-upload-scanner.md) supplied and operated separately; it must return a verdict bound to the exact content digest.

On 2026-09-24, the preflight passed against a disposable ClamAV 1.5.4 Linux daemon with signature database 28133, using image digest `clamav/clamav@sha256:0e31ce089574268aefa0b543767d66b70240ab51ed49eec53e07f18d5629d817` and a private shared Unix-socket volume. The test container and volume were removed. This verifies the live socket exchange and two control verdicts; it does not certify detection of every threat, future signature freshness, or a production scanner deployment.

`lib/uploads/local.ts` stores private mode-`0600` files under a mode-`0700` root on a single persistent host. Its exclusive hard-link publication prevents two racing writes from replacing one another. Keep the root outside web-served directories and back it up alongside the application database. `lib/uploads/supabase.ts` uses a private, 5 MiB, octet-stream-only bucket for Vercel + Supabase. It checks the bucket before each operation and creates no public or signed URL. A live Storage test found that two concurrent `upsert: false` calls to the same key can both be acknowledged. Do not use that primitive as an atomic claim: only the catalog winner may write the object.

`lib/uploads/catalog-contract.ts` defines owner-scoped metadata and an atomic quota reservation. SQLite, PostgreSQL, Supabase PostgREST and Convex adapters pass the same concurrency, isolation and deletion contract. The default quota is 20 active files and 50 MiB per owner, including pending, quarantined and deleting files; bytes are released only after object removal is confirmed. Deleted IDs remain tombstoned. `lib/uploads/intake.ts` validates bytes, reserves one new ID, writes the object and moves metadata to **quarantined**. If a write fails after storing bytes, it attempts deletion; failed cleanup remains in `deleting` with quota held for a later retry. An owner can retry deletion of a `deleting` row. If a request crashes while a row is still `pending`, the owner can delete it after 24 hours through the normal REST, CLI or MCP delete operation. The catalog atomically claims only a still-pending row for that owner and leaves quota held until object deletion succeeds. This owner-initiated recovery path also works without a scheduler. No durable released state exists; the optional scan-on-read path below makes a per-request release decision without changing catalog state.

For unattended recovery, run `npm run uploads:cleanup` from a source checkout with `npm ci` and the same data and object-store settings as the app, or invoke the protected HTTP trigger from a scheduler. One invocation examines at most 51 operator-only candidates and attempts cleanup on 50; its JSON result reports `scanned`, `deleted`, `skipped`, `failed` and `more` without names, owners or object keys. It selects `pending` and `deleting` rows whose reservation began at least 24 hours earlier. A pending row must still be pending when atomically claimed; a failed object deletion leaves its quota reserved in `deleting` for the next run. The command exits nonzero if any cleanup failed. Run it periodically, alert on failure, and continue invoking it while `more` is true; a persistent failed row can occupy a bounded batch until its object-store problem is resolved. It never deletes quarantined uploads or scans for unreferenced objects; owner downloads use the separate policy below.

For a managed scheduler, `GET /api/internal/uploads/cleanup` runs the same bounded pass and requires `Authorization: Bearer <CRON_SECRET>` with a server-only secret of at least 32 characters. An absent secret disables the route; a wrong one returns `401` before contacting either provider. A pass with failed deletions returns `503`, and all responses prohibit caching. The committed `vercel.json` schedules this route daily at 02:00 UTC for Vercel Production. Set `CRON_SECRET` even when uploads are disabled: an authorized disabled-storage invocation returns `storage_disabled` without contacting providers. When uploads are enabled, the managed configuration preflight requires Supabase Storage. Vercel sends a GET request and supplies the bearer secret automatically; its cron runs on production deployments, not previews. Drain old pending/deleting uploads before disabling their object backend, or cleanup cannot remove those objects. Self-hosted and cloud container schedulers can call the same protected route; the source-checkout CLI is available for operators who have the full development dependencies. The pruned production image does not include `tsx`, so invoke its HTTP route rather than running the TypeScript CLI inside that image. [Vercel Cron setup](https://vercel.com/docs/cron-jobs/quickstart) and [secret handling](https://vercel.com/docs/cron-jobs/manage-cron-jobs) describe the deployment behavior. The schedule is in the repository, but production delivery, logs, failures and `more` responses still need live monitoring after deployment.

For Supabase, apply the canonical migrations after Storage is installed. `20260924152111_private_upload_storage_policy.sql` adds a restrictive policy on `storage.objects`, so even a broad permissive policy cannot grant browser roles access to the quarantine bucket. Supabase already owns and enables RLS on that table; the migration must not alter the managed table. Plain PostgreSQL skips the Storage-specific policy. If Storage is installed after migrations were applied, apply the policy before provisioning the bucket. With operator-only `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_SECRET_KEY`, run `npm run check:upload-storage` to verify the policy and bucket; add `-- --create` to create only a missing bucket. The command refuses an existing public or misconfigured bucket. The backend secret bypasses Storage RLS, so the application must still derive every object key from a verified owner. See [Supabase private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) and [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

`npm run test:providers` checks the catalog on disposable PostgreSQL/PostgREST/Convex backends. `npm run test:upload-storage:live` additionally needs `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_ANON_KEY` and `DATABASE_URL` for a migrated, Storage-enabled **disposable** Supabase project with the private bucket provisioned. It exercises the real Storage API, anonymous denial and the composite one-writer quota race, and removes its objects. The usual `db:local:start` command excludes Storage; start a local stack with Storage enabled for this optional test. A local Storage/API/catalog run passed on 2026-09-24; hosted Storage remains unverified.

The opt-in quarantine API accepts uncompressed `application/octet-stream` requests at `POST /api/v1/uploads` with URI-encoded `x-upload-name` and `x-upload-media-type` headers. It streams at most 4 MiB, leaving room under [Vercel's 4.5 MB Function request limit](https://vercel.com/docs/functions/limitations). `GET /api/v1/uploads` returns active metadata and usage; `GET` and `DELETE /api/v1/uploads/{id}` inspect or remove an owned upload. By default no HTTP route returns file bytes. With scan-on-read enabled, `GET /api/v1/uploads/{id}/download` returns one owner-scoped attachment only after checking stored size, hash and type against catalog metadata and obtaining a fresh clean scanner verdict. Self-hosted processes may use the private Unix socket; distributed hosts may use the authenticated HTTPS endpoint. It returns `application/octet-stream` with no-store and no-sniff headers, never a public or signed URL. Registered Supabase users get upload read/write/download scopes. API keys require the separate `uploads:download` scope for bytes; existing `uploads:read` and `uploads:write` keys retain metadata/write access only. Issue an `uploads-download` or `uploads-full` key for this path. `npm run app -- uploads put FILE`, `list`, `get ID`, `download ID OUTPUT_FILE` and `delete ID` use the same authenticated API. The download writes a private mode-`0600` file atomically and refuses to replace an existing path. MCP exposes metadata listing, usage, get, delete and an owner-scoped metadata resource; it has no binary upload or download tool.

Each Node process admits at most four simultaneous download scans and one per owner. A request beyond either limit returns `429` before fetching object bytes or opening a scanner stream; retry after an active scan finishes. This bounds concurrent scan memory and sockets within one process, not across replicas or rapid sequential requests. Set ingress-level per-owner rate and concurrency limits for a multi-process or public self-hosted deployment, and monitor ClamAV capacity and signature freshness.

Monitor `GET /api/health/upload-scanner` on hosts with scanning enabled. It makes a bounded `zPING` to a Unix socket or an authenticated `GET` to the remote scanner, returning `200` with `status: ready` only after the expected response; missing, partial or unresponsive configuration returns `503` with `status: unavailable`. Concurrent callers share one probe, and the result is reused for five seconds per Node process to bound public health-check traffic; allow for that short reporting delay. An unconfigured scanner with scan-on-read disabled reports `disabled` with `200`. This route is separate from general application readiness so a scanner outage does not take records offline. It exposes no socket path, remote URL, token or daemon response. A liveness reply is not a signature test: use `npm run check:upload-scanner` for clean/EICAR verdict checks and maintain signatures separately.

Set `UPLOAD_STORAGE_PROVIDER=local` with a private persistent `UPLOAD_LOCAL_ROOT` for a self-hosted Node service, or `UPLOAD_STORAGE_PROVIDER=supabase` with server-only Supabase credentials for Vercel or another distributed host. Local storage refuses Vercel/Lambda. Metadata is still inspectable if the object backend is temporarily unconfigured, but writes/deletes fail closed. Apply all migrations; the additive upload-list function is required for PostgreSQL and Supabase. When a storage provider is configured, `/uploads` appears in the workspace. Signed-in Supabase users use their current account session; API-key users enter an upload-scoped key that stays in tab memory. The browser shows progress, server errors and quota usage, permits refresh/retry and owner deletion, and labels every stored file as quarantined. After a network failure, timeout or cancellation, refresh before retrying because the server might already have accepted the file. The browser, API and CLI store uploads in **quarantine only**, including files that passed the optional scanner. With `UPLOAD_DOWNLOAD_POLICY=scan-on-read`, an owner may request an attachment through the browser, REST or CLI; the server revalidates stored bytes and requires a fresh clean verdict from a private Unix-socket ClamAV daemon or an authenticated HTTPS scanner. Infected or unavailable scans release no bytes. The server never issues a reusable storage URL or backend credential. The real-Auth browser suite checks two signed-in users, account switching, cross-owner REST and MCP denial, owner MCP metadata access without bytes, and owner deletion against local private storage. This per-request release does not create a clean/rejected catalog state, safe extraction flow, durable review decision or short-lived download link. Quarantined bytes remain unavailable to Eve and MCP. Vercel accepts scan-on-read only with Supabase Storage and a complete remote scanner configuration; its preflight validates shape, not a live scanner. A production managed path still needs the scanner service deployed and monitored, a reviewed release policy, a deployed and monitored cleanup schedule, short-lived owner-authorized downloads and deletion of derived data. Hosted Storage and signed-in upload behavior on other data/object providers remain unverified.
