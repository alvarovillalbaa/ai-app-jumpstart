# Account chat

Account chat is opt-in and disabled by default. It reuses `useEveAgent` for live messages, follow-ups, approval responses and replay, after the application broker has resolved an owned runtime session. Browser clients cannot create Eve sessions directly, assign owners, select models, or set creation prices. Record API keys do not grant AI access.

Configure both the Next service and Eve runtime with:

- `AI_CHAT_ENABLED=true` and the same Supabase Auth settings (`AUTH_PROVIDER=supabase`, public Auth URL and publishable key).
- The same `DATA_PROVIDER` and backend credentials/database. Separate services must share the ownership and budget store; filesystem SQLite requires the same durable local file.
- The same explicit `APP_ORIGIN` in production, matching the browser-facing HTTPS origin. The shared application store validates this setting on both services.
- `AI_CREATION_SIGNING_JSON`: `{ "audience": "your-app:environment", "activeKey": "v1", "keys": { "v1": "<64 lowercase hex characters>" } }`. Generate 32 random bytes locally for each key, keep them server-only, and use a different audience/keyring per environment. For rotation, first distribute both keys to both services, then switch `activeKey`, and retain the old verification key through the outstanding signature window.
- `AI_RUNTIME_ORIGIN`: the fixed server-reachable origin serving `/eve/v1/session`. HTTPS is required except loopback. For the local supervisor this is `http://127.0.0.1:4274`. On Vercel this must be a pinned deployment/application origin reachable by the broker, with the Eve route mounted. Deployment protection must be configured separately; Vercel hosting alone does not establish reachability. A rejected/timed-out dispatch remains pending for reconciliation.
- `AI_BUDGET_POLICY_JSON`: a reviewed server policy as described in [usage budgets](usage-budgets.md). There are no default vendor prices. The configured agent remains `openai/gpt-5.6-luna-fast`; choose allowed runtime model IDs appropriate to that model and deployment.

Malformed enabled configuration fails closed. When account chat is enabled, the channel exclusively uses signed creation and verified user ownership, including during development. When disabled, only Eve's local development authenticator is available; production routes remain closed. Uploads and default tools remain disabled.

## Protocol and recovery

`POST /api/v1/conversations` accepts only `{ "message": "text", "operationId": "UUID" }` with a verified user bearer token. It reserves budget and an immutable operation before signed dispatch. A `202` response reports `starting` with `sessionId: null`. Only the winning runtime's receipt can make it `active`; HTTP acceptance alone cannot install a mapping. Identical retries share the operation; a changed request conflicts.

`GET /api/v1/conversations/:operationId` resolves only the authenticated owner's operation. Foreign and absent operations return `404`. `GET /api/v1/usage` returns that user's current UTC day, charged/reserved micro-USD, active/recent counts, unknown-cost count and daily ceiling. Open `/usage` from the account page to inspect it, or use CLI `usage` and MCP `usage_get`/`usage:///current` with a current registered-user token. These are application budget figures, not a provider invoice. Responses are not cached. Body/signature contents and credentials are excluded from application request logs.

In account mode `/s/:operationId` is an application operation locator, **not** an Eve session ID. The browser writes that URL before dispatch. It sends one creation request and then reads status; reload does not create another run. Once the receipt is active, the hook mounts with the owned session and replays its stream from index zero. Credentials are obtained afresh for each request/reconnect. Account changes immediately unmount the transcript and stream; this does not cancel server execution.

Status polling stops after one minute and offers **Check status**. An ambiguous start never automatically retries dispatch or refunds its reservation. If status is missing after a lost request, **Cancel pending start** can fence a budget-only reservation: it first installs a matching conversation tombstone, so a delayed dispatcher cannot create work. A genuinely absent operation returns `404` and is never presented as cancelled. New chat opens a separate conversation without deleting or cancelling the old one.

**Cancel pending start** calls `POST /api/v1/conversations/:operationId/cancel-start` with the current user's bearer token. For a budget-only operation it first creates a matching conversation reservation from the server-side ledger hash. The operation atomically revokes the reservation only while no runtime session has bound to it, then settles its budget at verified zero cost. Repeating a successful cancellation is safe. If the runtime binds first, the endpoint returns `409` and leaves its budget reserved for normal turn settlement; use the active turn's cancellation control if needed. A budget-store failure after revocation returns `503` and leaves the reservation charged until cancellation is retried or an operator reconciles it. A missing or foreign operation returns `404`. The screen never treats a connection error as proof of cancellation.

## Conversation history

Open `/conversations` from the account page or the chat's **History** link. Each successful reservation stores a title derived from the first 120 UTF-16 units of the initial message, with whitespace/control characters normalized and malformed Unicode repaired. This preview is private application data; it is not generated by a model. Creation retries never overwrite a renamed title. The list shows pending, active and revoked conversations; these are ownership states, not live run completion indicators. Opening a pending row reads its status and never resends its initial message.

- `GET /api/v1/conversations?limit=20&archived=false&cursor=…` lists the authenticated owner's conversations. `limit` is 1–50. Omit the cursor for the first page, then pass `nextCursor` unchanged until it is `null`. Ordering uses descending creation time and ID. Concurrent creations appear on refresh; pagination is not a snapshot. Summaries exclude runtime session IDs, request hashes and owner identifiers.
- `PATCH /api/v1/conversations/:operationId` accepts `{ "revision": 1, "title": "New title" }`, `{ "revision": 1, "archived": true }`, or both fields. Titles are trimmed, nonempty, at most 120 UTF-16 units and cannot contain control characters or malformed Unicode. A successful edit increments the revision. A stale revision returns `409`; foreign/missing operations return `404`. Refresh before editing again after a conflict or an uncertain network outcome.
- Archiving only changes list membership. It does not revoke ownership, delete messages, cancel work or refund usage. The archived filter offers **Restore**. Existing owned links continue to work.
- A pending row offers **Cancel pending start**. A successful cancellation becomes unavailable in history. Refresh after a `409` to see whether the runtime claimed it.

These endpoints require registered-user bearer credentials, like creation; record API keys do not grant access. The browser obtains fresh credentials and discards list/edit responses after account changes. A timeout is shown as an error rather than an optimistic success. History metadata is shared across SQLite, PostgreSQL, Supabase and Convex. `GET /api/v1/conversations/:operationId/metadata`, CLI `conversations` commands and MCP conversation tools/resources use the same metadata service; see [data access](data-access.md). Live transcript replay still comes from Eve. Selected finalized messages and run boundaries are also available through [stream projections](conversation-projections.md), including API/CLI/MCP reads and replay recovery. These projections can contain retried attempts and do not establish canonical model history.

For upgrades, apply the canonical SQL migrations before deploying PostgreSQL/Supabase applications. SQLite upgrades its local schema on connection. Legacy SQL rows use `createdAt: 0` and display **Date unavailable**, because no original timestamp was recorded. Convex retains its actual document creation time; run the bounded internal metadata backfill described in [database setup](databases.md) before opening legacy history.

## Validation and remaining scope

`npm run test:chat` provisions real isolated Supabase Auth, PostgreSQL and mail services, then runs the compiled Next app and a fresh compiled Eve app using the production channel and budget/ownership hooks. Only the model is deterministic. Its eleven browser contracts cover creation, replay, history, rename conflicts, archive/restore, follow-up, foreign-user denial, exhausted budgets, lost-response recovery, pending cancellation before a runtime receipt, budget-only cancellation, revoked credentials, structured drafts, approved artifacts, accessibility and a reusable two-user hosted smoke with one owned model turn. The receipt-race test waits for the runtime's failed boundary and confirms no model call. `npm run test:chat:container` runs the same contracts with Next and supervised Eve inside the production image; the test copies its compiled deterministic Eve fixture over the image's server output for that disposable run. Build with `npm run build:local` first, then build the image with `npm run test:container` or select an existing tag with `TEST_CONTAINER_IMAGE`. Docker and installed Chromium are required. The compiled local Eve port must be unused. These harnesses never use a hosted account or paid provider, and remove their temporary data and containers.

Materialized run views, exact source-order/canonical transcript projection, full account deletion/export, operator-wide visibility and reconciliation of disputed starts or failed settlements, reviewed model input/output price envelopes, and hosted deployment acceptance remain incomplete. A [paged application-visible export](data-access.md#export-visible-application-data) now covers current records, metadata, selected projections, saved artifacts and the usage snapshot, with an explicit omission manifest. Pending-only cancellation does not determine whether an unbound dispatch was ever received; its safety depends on the runtime binding before any model call. The current reservation ledger and call caps do not establish a guaranteed vendor invoice ceiling. See [delivery status](DELIVERY.md) before treating a deployment as release-ready.
