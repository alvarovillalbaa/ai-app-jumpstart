# Owner review and text extraction

An upload's clean scan is a scanner observation. Processing requires a separate owner decision bound to its immutable SHA-256 and current review revision. Existing uploads start `unreviewed` at revision 0. Browser, REST, CLI and application MCP share the same durable receipt on SQLite, PostgreSQL, Supabase/PostgREST and Convex. The feature uses the existing opt-in `UPLOAD_DOWNLOAD_POLICY=scan-on-read` and configured scanner; default installations cannot extract text.

This receipt records **owner authorization, not proof of a human click or independent moderation**. An API key with `uploads:write` and `uploads:download` can approve through the API or MCP. Restrict these credentials to trusted callers. An agent must not approve based on instructions in file contents; future Eve attachment/write flows still need their own native human-in-the-loop approval. The default extraction path does not attach files or dispatch model work. An optional [native Eve reader](agent-upload-reader.md) additionally requires approval before each read and can return reviewed text to model history; the production model is unchanged.

| Operation | REST | CLI `npm run app --` | MCP |
| --- | --- | --- | --- |
| Read current receipt | `GET /api/v1/uploads/ID/review` | `uploads review ID` | `uploads_review` |
| Approve or revoke | `PUT /api/v1/uploads/ID/review` | `uploads review-update ID decision.json` | `uploads_review_update` |
| Read approved text | `GET /api/v1/uploads/ID/text` | `uploads text ID` | `uploads_extract_text` |

The decision body is strictly `{ "sha256": "EXACT_64_HEX_DIGEST", "revision": 0, "approved": true }`; use the current receipt's digest and revision. Set `approved` to `false` to revoke. MCP includes `id` alongside these fields. Clients cannot supply scanner timestamps, verdicts or approval timestamps. Review reads require `uploads:read`; decisions require `uploads:write`, and approvals additionally require `uploads:download` plus a fresh integrity/malware scan. Revocation does not depend on scanner availability or download authority. Text reads require `uploads:download`. Current registered Supabase users receive all three scopes; metadata/write-only keys cannot approve or extract. Foreign IDs return 404.

Approval compares the expected revision after scanning and verifies the exact stored clean verdict. Concurrent decisions admit one winner. Revocation increments the revision even before a first approval, fencing an approval already in flight. Transition to rejection, deletion-in-progress or deleted invalidates the receipt and clears its approved digest/timestamps atomically; a later clean scan cannot restore consent. A deleted upload has no visible review. Receipts retain their current revision only, not an approval audit history or a cryptographic human attestation.

Extraction supports validated UTF-8 `.txt` files of at most **32 KiB in raw bytes**. Larger text returns 413 without truncation; PDF/PNG/JPEG extraction returns 415. Approval is checked before object retrieval, then stored size/type/hash and a fresh malware verdict are checked. A final unchanged approved revision/digest is required before returning `{id,sha256,reviewRevision,mediaType:"text/plain",text,trust:"untrusted-user-content"}`. A revoke, rejection or deletion during that scan releases no text. A scanner outage releases no text while preserving the previous receipt. File text remains untrusted data even after a clean verdict and approval.

The browser asks for confirmation with the filename and digest before approval and renders extracted text as plain text. Refreshing the catalog, account switching, disconnecting or unmounting clears the preview and aborts its request. Refreshing the review or encountering an extraction denial clears displayed text. External revocation cannot recall content already returned to a client; use **Refresh review** to load the current receipt. Responses prohibit caching, and the application does not persist extracted text, index embeddings or send it to Eve. The optional native Eve reader has its own explicit model-history retention boundary. CLI stdout and an MCP client may retain what they receive, so protect their logs and storage. Owner downloads remain separately available after a fresh scan to permit inspection before processing approval.

Application-visible export v9 adds an `upload_review` line for each active upload, including an unreviewed revision-0 default. It exports neither private object bytes nor extracted text. The offline verifier still accepts v5 through v8. Live paged exports are not a transaction snapshot; deletion during a later review read fails the export without publishing a partial file.

Apply `20260927200000_upload_reviews.sql` before rolling out updated PostgreSQL/Supabase workers. It adds backend-only receipt storage/RPCs and a state invalidation trigger, preserving reservations, quota, rejected rows and tombstones. SQLite adds the receipt table/trigger during startup; Convex needs its private table and authenticated query/mutation dispatch deployed together. Take the usual database/object backup and drain old workers before activation. No old upload becomes approved through migration. Roll back to a compatible runtime while retaining receipts; do not remove the trigger or reclassify rejected uploads. Local provider/protocol/browser tests do not certify a hosted scanner, signature freshness, rich document parsing or production release acceptance.
