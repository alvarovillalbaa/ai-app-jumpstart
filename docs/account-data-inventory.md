# Account data inventory

Full account export and erasure are not implemented. Use `npm run check:account-data-inventory` during schema changes. It compares the authoritative PostgreSQL/Supabase migrations, all SQLite table definitions under `lib/`, and the Convex schema against the classified inventory in `scripts/account-data-inventory.mjs`. An added or missing table, an unresolved owner join, or a missing direct-owner column fails CI. The check sees source declarations; it does not inspect a hosted database, Storage bucket, Auth project or running Eve world.

The inventory currently classifies 17 logical owner-linked entities. Records, creation receipts, conversations, budget accounts/days/reservations/corrections, uploads, preferences and request counters have direct tenant/subject ownership where their provider stores them. Conversation events/runs and artifacts follow their conversation; artifact versions follow their artifact; budget attempts follow their reservation; upload scan/review rows follow their upload. `internalNonces` is a global, expiring replay-control table without an owner key. Some providers compute data rather than store it in a separate table: SQLite has no budget-account/day table and Convex embeds upload scan decisions in uploads. PostgreSQL/Supabase currently have 17 classified application tables, SQLite has 16 and Convex has 17, each count including `internalNonces`.

The same manifest generates backend-only owner-row and orphan count queries for SQLite and PostgreSQL/Supabase. Their tests execute every query against real migrated schemas, with separate owners, retained child/tombstone controls and an orphaned budget-attempt control. A separate Convex operator audit pages through every classified owner table, resolving child ownership through its parent and counting unattributable orphans. The Convex HTTP action uses a distinct audit secret; the ordinary application backend secret cannot call it. Its allowlist is checked against the manifest, and both the emulator and disposable real Convex harness exercise the read-only path. Orphans cannot be attributed through the declared parent path, so any orphan count above zero requires investigation before an erasure claim. A deletion workflow can use these observations as one postcondition, but a zero count from a live database is not a fence against later writes. The queries are not exposed through the public application API, user-facing CLI or MCP and do not grant deletion authority.

Operators can run the **backend-only** read-only row inspection against a selected account. Set `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` in the process environment, then use `npm run account:inspect -- --sqlite /private/path/app.sqlite` or set `DATABASE_URL` and use `npm run account:inspect -- --postgres` for PostgreSQL or Supabase application tables. Do not put account identifiers or database credentials in command arguments. The command prints only per-entity counts and totals; it never prints the tenant, subject or connection URL. It checks the source inventory first, then uses one SQLite read transaction or one PostgreSQL repeatable-read, read-only transaction. The SQL path refuses an RLS-limited role that could silently report false zeroes. Missing tables, permissions and connection failures cause a generic diagnostic and no partial report. An orphan count is global to the application database and must be investigated before an erasure claim. A zero owner count is only a point-in-time application-row observation: it does not fence new writes or cover upload bytes, Auth, Eve/Workflow, external providers, logs or backups. The command does not delete data.

For Convex, set `CONVEX_SITE_URL` and a separate `CONVEX_AUDIT_SECRET` in the **operator process environment**, alongside the two account audit identity variables, then run `npm run account:inspect:convex -- --read-only`. Set that audit secret only in the Convex deployment and the operator environment, never in the web application or its `.env.local`. The command validates the source inventory, pages through the 16 owner-linked Convex tables, and emits only counts and totals. It fails without a complete report on an invalid page, service error or page limit. Each bounded page is its own Convex read snapshot, so concurrent writes can move between pages; this is less consistent than the SQLite/PostgreSQL report and cannot certify zero remaining rows. It excludes the global expiring nonce table, which has no account owner.

Inspect private upload bytes separately with `npm run account:inspect:objects -- --read-only`. Set the same `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` plus `UPLOAD_STORAGE_PROVIDER=local|supabase|aws-s3` and that provider's normal operator-side storage settings in the process environment. The command counts all objects under the account's opaque storage namespace, including bytes whose catalog row is gone, and prints no object key, filename, account identity or credential. Local inspection requires the private persistent `UPLOAD_LOCAL_ROOT` and refuses symlinks or unexpected nested entries. Supabase inspection checks the private bucket, then pages its Storage listing using an operator backend key. AWS inspection checks public-access blocks and never-enabled versioning, then pages `ListObjectsV2`; the operator role needs `s3:ListBucket` on the bucket. Neither cloud listing is a consistent snapshot under concurrent writes. A zero count does not cover keys outside this namespace, versioned/unfinished uploads, derived copies, other stores or backups, and does not fence a late upload. The command never deletes objects.

An account closure still needs a durable owner-wide write fence and handling for active Eve turns, pending starts and callbacks. It must coordinate private object bytes and metadata, immutable budget corrections, application rows and tombstones, Auth identities/sessions, runtime streams and auxiliary runs, connector/provider copies, logs and backups. The existing application-visible export omits several of these categories. Do not label its output a complete account export or expose a "Delete account" control until the full cross-system workflow and its postconditions exist.
