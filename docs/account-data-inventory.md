# Account data inventory

To package **both** raw application rows and private object bytes for one fenced account, set the same operator identity, metadata backend and `UPLOAD_STORAGE_PROVIDER` environment variables, stop all application, Eve and object cleanup writers, then run `npm run account:export:bundle -- --metadata sqlite|postgres|convex --output /private/new-bundle --stopped`. The output must be a new directory under a real mode-0700 private parent; it cannot sit inside the local object source. The command writes `rows.ndjson` and `objects.ndjson`, verifies both, checks their owner binding and matches each active upload catalog row to object size and SHA-256, then publishes `manifest.json` last. An object with no catalog row is preserved and counted; a pending, deleting or deleted row without bytes is counted; a quarantined, clean or rejected row without matching bytes fails and removes the incomplete directory. The v2 manifest also binds object erasure to the selected local root path/device/inode, Supabase project origin and bucket, or S3 region and bucket without publishing those coordinates. Run `npm run account:verify:bundle -- /private/new-bundle` offline to recheck hashes, permissions, archive contents, owner binding and catalog relation. Older v1 bundles remain verifiable but need a new v2 export before object erasure. Keep the whole directory private and out of version control. The manifest is a completion marker and an integrity check, **not** an authenticity signature. The two backends are read sequentially without a cross-service transaction; the permanent row fence does not fence object writes, and `--stopped` is only an operator assertion. This bundle does not include Auth, Eve/Workflow, external/provider or derived copies, object versions, unfinished uploads, logs or backups, and there is no production account import/restore command. It is **not** a full account export or erasure certificate.

For an **offline recovery rehearsal** of a bundle with SQLite metadata and local, Supabase Storage or S3 object bytes, run `npm run account:rehearse:bundle -- --source /private/new-bundle --output /private/new-rehearsal`. The destination must be a new directory under a private parent, outside the source bundle. It creates a fresh current-schema SQLite database, imports every owner-linked row with exact int64 values, restores every archived object into local storage including catalog orphans, and installs the permanent application-row fence. A manifest is published only after every row and object is compared back to the source. Run `npm run account:verify:rehearsal -- /private/new-bundle /private/new-rehearsal` to recheck the source, restored rows, bytes, foreign-row absence and fence. Failed attempts remove their new directory; existing targets are never replaced. This is an isolated rehearsal for the same SQLite schema, not a live application install or an account reactivation. It does not restore Auth, Eve/Workflow state, global nonces, provider copies, logs or backups. The source bundle and rehearsal are sensitive and their hashes are integrity checks, not signatures.

For a **rollback-only PostgreSQL/Supabase row-import rehearsal**, create a separate empty loopback database named `app_account_rehearsal_*` and set its private URL in `ACCOUNT_REHEARSAL_DATABASE_URL`. Apply this checkout's exact migrations and rehearse a verified PostgreSQL-metadata bundle with:

```sh
DATABASE_URL="$ACCOUNT_REHEARSAL_DATABASE_URL" npm run db:migrate
npm run account:rehearse:postgres -- --source /private/new-bundle
```

The command refuses a nonempty or migration-drifted target and an RLS-limited role. Inside one read-committed transaction it imports every classified owner row, including children and exact bigint values; temporarily suppresses only the run-cache derivation trigger because run rows are already archived; compares normalized full rows and foreign-row absence; verifies the bundle again; and rolls back. It confirms the target remains empty before reporting `rolled-back-rehearsal`. The bundle's object bytes are verified offline but **not restored** by this command. This is a schema/row compatibility proof against a disposable local database, not a persistent account restore, a hosted Supabase test or an account reactivation.

Full account export and erasure are not implemented. Use `npm run check:account-data-inventory` during schema changes. It compares the authoritative PostgreSQL/Supabase migrations, all SQLite table definitions under `lib/`, and the Convex schema against the classified inventory in `scripts/account-data-inventory.mjs`. An added or missing table, an unresolved owner join, or a missing direct-owner column fails CI. The check sees source declarations; it does not inspect a hosted database, Storage bucket, Auth project or running Eve world.

The inventory currently classifies 17 logical owner-linked entities. Records, creation receipts, conversations, budget accounts/days/reservations/corrections, uploads, preferences and request counters have direct tenant/subject ownership where their provider stores them. Conversation events/runs and artifacts follow their conversation; artifact versions follow their artifact; budget attempts follow their reservation; upload scan/review rows follow their upload. `internalNonces` is a global, expiring replay-control table without an owner key. Some providers compute data rather than store it in a separate table: SQLite has no budget-account/day table and Convex embeds upload scan decisions in uploads. PostgreSQL/Supabase currently have 18 classified tables, SQLite has 17 and Convex has 18. Each count includes `internalNonces` and one durable `accountFences` closure-control table. Neither control table is an owner-row export or erasure target.

The same manifest generates backend-only owner-row and orphan count queries for SQLite and PostgreSQL/Supabase. Their tests execute every query against real migrated schemas, with separate owners, retained child/tombstone controls and an orphaned budget-attempt control. A separate Convex operator audit pages through every classified owner table, resolving child ownership through its parent and counting unattributable orphans. The Convex HTTP action uses a distinct audit secret; the ordinary application backend secret cannot call it. Its allowlist is checked against the manifest, and both the emulator and disposable real Convex harness exercise the read-only path. Orphans cannot be attributed through the declared parent path, so any orphan count above zero requires investigation before an erasure claim. A deletion workflow can use these observations as one postcondition, but a zero count from a live database does not establish whether a separate write fence exists. The queries are not exposed through the public application API, user-facing CLI or MCP and do not grant deletion authority.

Operators can run the **backend-only** read-only row inspection against a selected account. Set `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` in the process environment, then use `npm run account:inspect -- --sqlite /private/path/app.sqlite` or set `DATABASE_URL` and use `npm run account:inspect -- --postgres` for PostgreSQL or Supabase application tables. Do not put account identifiers or database credentials in command arguments. The command prints only per-entity counts and totals; it never prints the tenant, subject or connection URL. It checks the source inventory first, then uses one SQLite read transaction or one PostgreSQL repeatable-read, read-only transaction. The SQL path refuses an RLS-limited role that could silently report false zeroes. Missing tables, permissions and connection failures cause a generic diagnostic and no partial report. An orphan count is global to the application database and must be investigated before an erasure claim. A zero owner count is only a point-in-time application-row observation: the inspection itself does not fence new writes or cover upload bytes, Auth, Eve/Workflow, external providers, logs or backups. The command does not delete data.

For Convex, set `CONVEX_SITE_URL` and a separate `CONVEX_AUDIT_SECRET` in the **operator process environment**, alongside the two account audit identity variables, then run `npm run account:inspect:convex -- --read-only`. Set that audit secret only in the Convex deployment and the operator environment, never in the web application or its `.env.local`. The command validates the source inventory, pages through the 16 owner-linked Convex tables, and emits only counts and totals. It fails without a complete report on an invalid page, service error or page limit. Each bounded page is its own Convex read snapshot, so concurrent writes can move between pages; this is less consistent than the SQLite/PostgreSQL report and cannot certify zero remaining rows. It excludes the global expiring nonce table, which has no account owner.

To preserve the selected account's **raw application rows** after setting a permanent row fence and stopping all application, Eve and cleanup writers, run `npm run account:export:rows -- --metadata sqlite|postgres|convex --output /private/new-rows.ndjson --stopped`. Use the same operator account and metadata-backend environment as `account:fence:rows`. The command requires a real mode-0700 destination directory and an unused filename. It verifies the fence and guard coverage, refuses global child orphans, captures every classified owner-linked table including child rows and tombstones, compares per-entity counts, and publishes only a complete mode-0600 NDJSON archive with a whole-file SHA-256 digest. SQLite and PostgreSQL/Supabase use one read transaction; PostgreSQL retains numeric JSON as source text, while SQLite tags int64 and blob values to avoid loss. Convex uses at most 10,000 bounded pages and compares operator counts before and after; its pages are separate snapshots, so `--stopped` is an operator assertion needed to exclude concurrent deletion. The archive is capped at 100,000 owner rows and 512 MiB and has no persistent restore/import command. Run `npm run account:verify:rows -- /private/new-rows.ndjson` offline to verify the archive's shape, counts and digest. This is an integrity check, not an authenticity signature. Account identifiers and raw private content are inside the archive, but not in CLI output. Global nonces and fence control rows are excluded. Private object bytes, Auth, Eve/Workflow, provider copies, logs and backups require separate preservation; this is **not** a full account export or erasure certificate.

Inspect private upload bytes separately with `npm run account:inspect:objects -- --read-only`. Set the same `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` plus `UPLOAD_STORAGE_PROVIDER=local|supabase|aws-s3` and that provider's normal operator-side storage settings in the process environment. The command counts all objects under the account's opaque storage namespace, including bytes whose catalog row is gone, and prints no object key, filename, account identity or credential. Local inspection requires the private persistent `UPLOAD_LOCAL_ROOT` and refuses symlinks or unexpected nested entries. Supabase inspection checks the private bucket, then pages its Storage listing using an operator backend key. AWS inspection checks public-access blocks and never-enabled versioning, then pages `ListObjectsV2`; the operator role needs `s3:ListBucket` on the bucket. Neither cloud listing is a consistent snapshot under concurrent writes. A zero count does not cover keys outside this namespace, versioned/unfinished uploads, derived copies, other stores or backups, and does not fence a late upload. The command never deletes objects.

To preserve the actual private object bytes for a selected account, stop all application, Eve and upload cleanup writers to that object store, then run `npm run account:export:objects -- --output /private/new-objects.ndjson --stopped` with the same operator account and storage environment. The destination's parent must be a real mode-0700 private directory and the output path must not exist. The command lists all UUID objects under the owner namespace, including catalog orphans; reads each bounded raw object without applying a clean scan verdict; writes its ID, size, SHA-256 and base64 bytes to a mode-0600 file; lists again; and atomically publishes only after both listings match. Local reads reject symlinks, permissive file modes and changed file metadata. S3 needs `s3:GetObject` plus `s3:ListBucket`; Supabase needs the backend Storage key. Run `npm run app -- export verify /private/new-objects.ndjson` offline to verify the whole-file and per-object digests. Keep this sensitive artifact out of version control and do not serve it from the app. A failure leaves no published file. The `--stopped` flag records an operator assertion, not an enforced write fence: provider listings and object contents are not a cross-service transaction, and byte replacement between reads may evade detection. The export omits application metadata, Auth, Eve/Workflow, provider/derived copies, versions, unfinished multipart uploads and backups. It is **not** a full account export or an erasure certificate.

For one operator report spanning both application rows and the selected private object store, run `npm run account:inspect:closure -- --metadata sqlite --read-only`, changing `sqlite` to `postgres` for PostgreSQL/Supabase application tables or `convex` for Convex. Set the same account identity and object-provider environment variables as above. SQLite also needs an absolute `ACCOUNT_AUDIT_SQLITE_PATH`; PostgreSQL/Supabase needs `DATABASE_URL`; Convex needs `CONVEX_SITE_URL` and the separate operator `CONVEX_AUDIT_SECRET`. The command validates the classified source inventory, completes both inspections before printing anything, and reports per-entity owner rows, **global** unattributable child rows and objects under the selected owner prefix. `retained_or_unattributable` means at least one count is nonzero. `unfenced_zero` means these two observations returned zero and the command did not establish or verify a write fence; it is never a deletion or retention certificate. The row and object reads are separate snapshots, and global orphan rows may belong to a different account. A backend failure produces a generic diagnostic and no partial report. Keep account identifiers and secrets in the operator process environment, not command arguments or an app `.env.local`.

For a self-hosted **PostgreSQL Workflow** world, run `npm run account:inspect:workflow -- --metadata sqlite --read-only`, changing `sqlite` to `postgres` for PostgreSQL/Supabase application metadata. Set `ACCOUNT_AUDIT_TENANT`, `ACCOUNT_AUDIT_SUBJECT`, `WORKFLOW_POSTGRES_URL`, and either absolute `ACCOUNT_AUDIT_SQLITE_PATH` or operator `DATABASE_URL` in the process environment. The command reads bound session IDs from the selected application's conversations, then counts Workflow runs reachable through Eve's parent/root attributes and their steps, events, hooks, stream chunks, waits and event slots. It emits only counts, never IDs or URLs, and refuses an unknown or RLS-restricted Workflow schema. `otherSessionRoots` is a **global** count of Eve session runs outside this account's bindings, including other accounts; it cannot be assigned to this owner. The two databases are separate read snapshots. An absent binding, an auxiliary run without Eve lineage, or a deleted application conversation may leave account data unlinked; local and Vercel-managed Workflow are outside this command. Even zero linked runs is not proof of account erasure. This is an inspection aid before a separate Workflow export/retirement procedure, not part of the row/object closure report or an erasure certificate.

After creating and securing a source-bound v2 account bundle, operators of a self-hosted PostgreSQL Workflow world can preserve its **linked native rows** with `npm run account:export:workflow -- --source /private/bundle --output /private/new-workflow.ndjson --stopped`. Set the same `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` as the bundle and `WORKFLOW_POSTGRES_URL` in the operator process. Stop all application and Eve/Workflow writers first; `--stopped` is an assertion, and the command refuses currently locked Graphile jobs. It verifies the bundle, derives session IDs from its archived conversation rows even if live application rows have since been removed, and captures each linked Workflow run and its steps, events, hooks, stream chunks, waits and event slots in one read-only PostgreSQL snapshot. The output is a new mode-0600 NDJSON file with a content digest and the source bundle manifest hash. It fails without publishing if a row count, schema, source bundle or size bound changes. Verify later, offline and without database credentials, with `npm run account:verify:workflow -- --source /private/bundle --archive /private/new-workflow.ndjson`; the verifier checks hashes, row counts and Eve lineage against that exact bundle. Keep both artifacts private. This is a forensic archive without a production restore command or authenticity signature. It omits unlinked/auxiliary runs, Graphile job payloads, local or Vercel-managed Workflow, Auth, external providers, logs and backups; it does not delete Workflow data or make the combined bundle a full account export. Use the separate whole-database Workflow backup for operational recovery.

To test whether this account archive can be imported by the current native Workflow schema, create a separate empty loopback PostgreSQL database named `workflow_account_rehearsal_*`, set its private URL as `ACCOUNT_REHEARSAL_WORKFLOW_URL`, and migrate it with `WORKFLOW_POSTGRES_URL="$ACCOUNT_REHEARSAL_WORKFLOW_URL" npm run workflow:migrate`. Then run `npm run account:rehearse:workflow -- --source /private/bundle --archive /private/new-workflow.ndjson`. The command verifies the source-bound archive and exact installed Workflow migration ledger, rejects a nonempty or restricted Workflow target and pending Graphile jobs, imports every archived native row in one transaction, compares exact restored row hashes, rolls back, and checks that the target remains empty. It requires no source Workflow connection and prints only counts. Do not use a production target: the hostname must be loopback and the database name must have the rehearsal prefix. This proves a current-schema row import for the linked archive, not a runnable Eve session, production restore, full account export or erasure. Keep the disposable database private and drop it after inspection.

A permanent application-row write fence is available for each metadata provider through `npm run account:fence:rows -- --metadata sqlite|postgres|convex --set-permanent`. Set `ACCOUNT_AUDIT_TENANT` and `ACCOUNT_AUDIT_SUBJECT` in the operator process environment. SQLite additionally needs an absolute `ACCOUNT_AUDIT_SQLITE_PATH` to an initialized database; PostgreSQL/Supabase needs an operator `DATABASE_URL` after migrations; Convex needs `CONVEX_SITE_URL` and `CONVEX_AUDIT_SECRET`. The command validates the source inventory and backend guard coverage, then inserts an idempotent, immutable fence row. It prints only provider, status, whether it created the row, and scope; it never prints the account identity or credentials. There is no un-fence operation. After it commits, later application-row inserts and updates for that owner fail, including child rows; reads and physical deletion remain available. The Eve session authorizer also reads this fence before accepting a new session, follow-up, approval response, clear or compact request; an owner may still stream, cancel or reset a bound session so a closing account can be retired. Upload intake reserves a guarded metadata row before writing bytes, rechecks the fence after scanning, and tries to remove its fresh object if a fence blocks later metadata cleanup. The Supabase status RPC is backend-only, and a missing or failed fence read denies new Eve input and upload storage. SQLite serializes writers, PostgreSQL uses a per-owner transaction advisory lock and requires read-committed writes, and Convex checks the indexed fence in each owner mutation transaction. A pending write may complete before the fence commits. These checks are not an atomic fence on in-flight Eve turns, callbacks, Workflow state or private object bytes; a failed object deletion remains possible and the fenced metadata row stays for inspection. Stop all writers and inspect outstanding work before export or erasure. Set a fence only after deciding that this account must permanently stop application-row writes; back up and rehearse the closure procedure separately.

For private upload bytes, first run `npm run account:erase:objects -- --source /private/new-bundle --stopped --plan` with the same owner, selected metadata backend, and `UPLOAD_STORAGE_PROVIDER=local|supabase|aws-s3` settings used for the bundle. The command requires a new source-bound v2 bundle, compares the selected source fingerprint before listing, verifies the entire private bundle, runs the metadata row-erasure plan to confirm the permanent fence and unchanged rows, then checks that every currently stored object under this owner prefix is archived with the same size and SHA-256. A different local directory at the same path or a different configured cloud bucket/project fails before deletion. Changed or unarchived bytes fail before deletion; an already removed subset is allowed so an interrupted run can resume from the same bundle. After securing the bundle and stopping all application, Eve and cleanup writers, replace `--plan` with `--erase-private-objects`. Deletions happen one object at a time and are **not atomic**; an error may leave some objects removed. The command reports success only after another owner-prefix listing is empty. Run row erasure afterward while metadata still matches the archive. Local storage must be a private persistent directory; Supabase Storage requires its backend key; S3 requires a private never-versioned bucket and `s3:ListBucket`, `s3:GetObject` and `s3:DeleteObject` on the intended scope. The fingerprint is an operator configuration check, not proof against a redirected service, reused bucket name or concurrent source change. The command does not fence late object writes, erase object versions or unfinished uploads, or remove Auth, Eve/Workflow, derived/provider copies, logs or backups. It is an operator step, not complete account closure.

For fenced application rows, a backend operator can first run `npm run account:erase:rows -- --metadata sqlite|postgres|convex --source /private/new-bundle --stopped --plan`. The plan requires a verified combined row-and-object bundle for the exact owner and metadata provider, a permanent row fence, classified schema and zero unattributable child rows. SQLite and PostgreSQL/Supabase compare exact per-entity archive-to-live counts inside a write transaction that rolls back in plan mode. After securing the bundle and stopping all writers, replace `--plan` with `--erase-application-rows` to delete the owner's rows in child-before-parent order. Each SQL/SQLite delete count must match the archive and zero owner rows must remain before commit; a mismatch rolls back the transaction. The permanent fence remains.

Convex uses bounded read pages to prove every remaining owner row still exactly matches one archived row. Its operator endpoint requires both `CONVEX_AUDIT_SECRET` and a different `CONVEX_ERASURE_SECRET` in the Convex deployment and operator process for execution; the plan needs only the audit secret. Each mutation rechecks the permanent fence, table ID and owner before deleting at most 10 rows. These batches are **not one transaction**: after an interruption, rerun the same command with the same verified bundle. It accepts a subset of archived rows and rejects changed, extra, foreign or unattributable rows. The final inspection must find zero owner rows and zero global child orphans before success is reported. A failed run may already have deleted some rows. These row-erasure paths do not delete private object bytes, Auth, Eve/Workflow or provider copies, so their result is not account closure. The bundle and `--stopped` assertion are operator controls; they are not an authenticity signature or an enforced cross-system fence.

For an account using Supabase Auth, after the selected private object bytes and application rows are erased, run `npm run account:erase:auth -- --source /private/new-bundle --stopped --plan` with `AUTH_PROVIDER=supabase`, the exact `ACCOUNT_AUDIT_TENANT=supabase:<SUPABASE_AUTH_URL origin>` and `ACCOUNT_AUDIT_SUBJECT=<Auth user UUID>`, a separate operator `SUPABASE_AUTH_ADMIN_KEY` (secret or service-role key), and the same metadata/object backend settings used for the bundle. The command verifies the source-bound v2 bundle, exact Auth origin and subject, object source, permanent row fence and guards, zero owner rows, zero global unattributable rows, and zero selected owner-prefix objects. It then fetches the exact registered Auth user through the admin API. Once the plan succeeds and all writers remain stopped, replace `--plan` with `--erase-auth-identity` for a hard delete; it verifies that a follow-up admin lookup returns 404. An interrupted run can be retried and reports `auth-identity-already-absent` after the same prerequisites pass. Keep the admin key only in the operator process, never the app environment. The CLI prints no email, user ID, key or backend URL. This step does not export Auth metadata or establish a cross-system transaction or object write fence. [Supabase notes](https://supabase.com/docs/guides/auth/managing-user-data) that deleting an Auth user removes its sessions and refresh-token path, while previously issued access JWTs can remain usable until expiry; Storage-owned objects can block deletion. Eve/Workflow state, provider copies, logs and backups still need separate handling, so this is not full account closure.

A full account closure still needs an owner-wide cross-system fence and handling for active Eve turns, pending starts and callbacks. It must coordinate private object bytes and metadata, immutable budget corrections, application rows and tombstones, Auth identities/sessions, runtime streams and auxiliary runs, connector/provider copies, logs and backups. The existing application-visible export omits several of these categories. Do not label its output a complete account export or expose a "Delete account" control until the full cross-system workflow and its postconditions exist.
