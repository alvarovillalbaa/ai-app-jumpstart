# Testing

The manually dispatched [Hosted acceptance workflow](../.github/workflows/hosted-acceptance.yml) runs the exact deployed OpenAPI/REST contract plus browser records and REST/CLI/MCP ownership checks from the default branch against one configured staging deployment. Set up the `hosted-staging` GitHub environment and its reviewer rule and disposable credentials first; the smoke does not deploy or call a model. See the [configuration and limits](hosting.md#github-actions-hosted-acceptance).

CI runs `npm audit --audit-level=high` against the complete pinned dependency graph, including build and test packages. It also uploads a CycloneDX inventory generated by `npm run --silent sbom > dependency-sbom.cdx.json` from the committed lockfile, including optional packages for other platforms. Run the same commands before a release; the audit reflects the advisory registry at execution time, while the SBOM is an inventory rather than a provenance attestation or license review. The generated file is ignored locally.

`npm run check:container-pins` guards the Dockerfile frontend, external Dockerfile bases and Compose service images, and checks that the real-account PostgreSQL harness uses the same pinned image as Compose. It checks committed references, not registry availability or a successful image build; the CI container and browser jobs supply those runtime checks.

`npm run check:openapi` compares the committed public OpenAPI 3.1 artifact with every authored `/api/v1` route and exported HTTP method. The production browser suite also fetches the served artifact. The check catches omitted or stale operations; payload details still require review against the shared service contracts when an endpoint changes.

`npm run account:export:bundle -- --metadata sqlite|postgres|convex --output /private/new-dir --stopped` creates a private combined application-row and object-byte archive for one fenced owner; `npm run account:verify:bundle -- /private/new-dir` checks it offline. Focused SQLite/local and Convex emulator tests cover active bytes, orphan preservation, isolation, mismatch cleanup, tamper refusal and no-clobber; disposable PostgreSQL/Supabase and real Convex harnesses exercise the operator command. The disposable managed-account fixture also uses real Supabase Storage bytes with a nonempty PostgreSQL upload catalog, checks an orphan and foreign-owner isolation, and refuses unfenced and mismatched-byte bundles. This requires stopped writers and operator credentials for both stores; the reads are not a cross-service transaction, and Auth/Eve data and production restore remain outside the bundle.

`npm run account:rehearse:bundle -- --source /private/bundle --output /private/new-rehearsal` restores a SQLite-metadata bundle with local, Supabase Storage or S3 object bytes into a new isolated, fenced SQLite database and private local-object root; `npm run account:verify:rehearsal -- /private/bundle /private/new-rehearsal` compares all rows and object bytes. The focused test covers exact int64 preservation, child rows, foreign-row and tamper rejection, no-clobber and both CLIs. This is offline same-schema rehearsal, not a live app install or full account recovery.

`npm run account:rehearse:postgres -- --source /private/bundle` verifies a PostgreSQL-metadata bundle, imports its rows into an empty current-schema loopback `app_account_rehearsal_*` database named by `ACCOUNT_REHEARSAL_DATABASE_URL`, compares every restored owner row, then rolls back and verifies the target is empty. `test:postgres` and `test:supabase` exercise the command with parent/child rows, a large identity value and a nonempty-target refusal. Bundle object bytes are verified, not imported; this is not persistent or hosted account recovery.

`npm run test:amplify-build` builds the native Amplify self-managed adapter, checks its real CloudFormation graph offline and invokes its generated Node 24 streaming handler against disposable PostgreSQL. It reuses two-owner REST/CLI/MCP and seven public browser/accessibility/CSP contracts, verifies the protected cleanup route remains `storage_disabled` because this stack does not provision uploads, and checks compiled per-owner request counters and quota rejection across REST/CLI/MCP without a rejected write. Private-upload behavior is covered by the provider-specific suites below. `npm run test:amplify-ingress` requires Docker and checks the actual guarded Eve ingress, readiness and incremental SSE. These fixtures do not emulate AWS or prove hosted registered-user chat, Workflow recovery or a paid production-model turn; see [the Amplify recipe](amplify-self-managed.md).

Its explicit `--supabase` mode creates a separate application database in its disposable PostgreSQL container, starts the real `supabase/storage-api:v1.74.0` service so its own migrations create the Storage schema, then applies the canonical application migrations and starts the existing checksum-pinned PostgREST binary. Auth, REST and Storage prefixes share one loopback gateway. The private bucket is provisioned through the normal `check:upload-storage --create` command after the restrictive policy passes. The service version follows the [official self-hosting Compose configuration](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml); service bytes use an isolated container file volume, while the application selects its production Supabase object adapter. Real signed user tokens are checked by both Auth and PostgREST; the application uses a separate generated service-role token for backend database work. Account, budget, artifact, projection, upload-catalog/review, preferences and request-limit operations use the production Supabase adapters. Fixture seeding uses the selected store contracts so SQL aggregates and audit rows remain consistent. The harness fails if it creates a SQLite application database or local application upload directory and removes its own processes, containers, volumes and private configuration after success or failure.

Run the three named commands above, or pass `--supabase` to the host Auth/chat harness; it rejects combination with `--container` before creating resources. The account mode also checks real registered users and the anonymous role cannot read 17 backend-only tables, forge a record, or call budget/preferences/admission/upload-review RPCs, even with their own verified owner strings. The API writes are checked directly with the disposable backend credential to prove they reached PostgreSQL. The account mode runs the reusable live Storage contract, including a concurrent intake quota race. A deliberately broad object policy in this disposable database permits reads/writes to an unrelated private bucket; the application quarantine policy still denies downloads, signed URLs, inserts, replacements, listing and deletion to anonymous users, the uploader and another registered user. Backend reads prove attempts preserve private bytes, and owner API deletion removes them. The reviewed-upload mode runs approved text extraction and the native reader against the real Storage service. This is joint local Auth/application-database/Storage/runtime proof. Hosted Storage/S3, production SMTP, deployed Gateway/Workflow retention, hosted networking and paid-model acceptance remain separate checks. CI runs all three modes in the `supabase-accounts` job in addition to the existing SQLite/browser and production-container jobs.

The PostgreSQL harness checks the read-only migration dry run before applying schema and again after an idempotent rerun, then verifies both modes reject a ledger migration absent from this checkout.
