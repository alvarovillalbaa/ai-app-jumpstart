# Cloud upload cleanup jobs

Cloud uploads retain quota for abandoned `pending` and failed `deleting` rows until the protected cleanup route removes their private objects. The [runtime cloud preflight](cloud-containers.md) requires a managed `CRON_SECRET` reference when uploads are enabled. Generate a separate scheduled job from the same reviewed, filled runtime manifest so the job uses the exact deployed app image digest and origin. It calls the application over HTTPS; it does not need database, object-store, model or Workflow credentials.

```sh
npm run cloud:cleanup-job -- --provider aws --file PRIVATE_RUNTIME.json \
  --name staging-upload-cleanup --output PRIVATE_CLEANUP_JOB.json
```

Use `azure` or `gcp` for the other runtime manifests. The command validates the source release, refuses disabled uploads, selects only `APP_ORIGIN` and the managed `CRON_SECRET` reference, and creates a mode-`0600` JSON file without overwriting an existing file. It does not read secret values, contact a cloud API, create a schedule or execute cleanup. Review the file and its identity before submitting it. The job runs `node scripts/run-upload-cleanup.mjs` from the pinned production image. One execution follows `more` for up to 20 bounded passes, rejects redirects, emits aggregate counts only, and exits nonzero on endpoint errors, malformed results or remaining backlog. A persistent failed row requires object-store repair. See [upload cleanup semantics](uploads.md).

| Provider | Generated artifact | Scheduling step |
| --- | --- | --- |
| AWS ECS/Fargate | One-container task definition with the selected Secrets Manager ARN and no app/ingress health check or task role | Register it, then use EventBridge Scheduler to run that task revision at least daily |
| Azure Container Apps | Scheduled job with a 02:00 UTC five-field cron, one replica, a 900-second deadline and selected Key Vault secret | Register the job and inspect its schedule |
| Google Cloud Run | One-task job with a 900-second deadline and selected Secret Manager version | Register it, then use Cloud Scheduler to invoke the job at least daily |

The generator reuses the runtime image-pull identity, compute resources and selected log configuration. AWS inherits the execution role, Azure inherits the user-assigned identity, and GCP inherits the service account. Replace those with a dedicated cleanup identity where practical: image pull, log write and access to this one cleanup secret are sufficient for the job itself. On AWS, the EventBridge schedule additionally needs a task-launch role and the private subnet/security-group configuration; the job needs outbound access to the public application origin. Azure private registry configuration must be identity-based, or generation fails. GCP copies only a Secret Manager alias annotation when present; add reviewed egress settings if the environment requires them. Keep the scheduler secret distinct per environment and make its reference resolve to the same value as the running app's `CRON_SECRET`.

For AWS, register the reviewed task definition with `aws ecs register-task-definition --cli-input-json file://PRIVATE_CLEANUP_JOB.json`. Create an [EventBridge Scheduler ECS task target](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/tasks-scheduled-eventbridge-scheduler.html) for the resulting revision and cluster, with the reviewed network and task-launch role. First run the task manually using `aws ecs run-task`; wait for it to stop and require the cleanup container exit code to be zero. Registration and schedule creation alone do not prove the runner can reach the application. The task definition intentionally omits the web health check; ECS monitors task-definition health checks, not an image-only check ([ECS health-check behavior](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/healthcheck.html)).

For Azure, create the [scheduled Container Apps job](https://learn.microsoft.com/en-us/azure/container-apps/jobs) with `az containerapp job create --name JOB --resource-group GROUP --yaml PRIVATE_CLEANUP_JOB.json`. The generated cron runs daily at 02:00 UTC; edit and review it if another time is required. Start one execution with `az containerapp job start --name JOB --resource-group GROUP`, then require a successful terminal execution and inspect the aggregate log line. The one automatic retry handles a transient request failure; alert on final failure. Confirm the schedule is enabled and fires after registration.

For GCP, register with `gcloud run jobs replace PRIVATE_CLEANUP_JOB.json --region REGION --project PROJECT` and execute once with `gcloud run jobs execute JOB --region REGION --project PROJECT --wait`. Require a successful execution and inspect the aggregate log line. Set a [Cloud Scheduler trigger](https://docs.cloud.google.com/run/docs/execute/jobs-on-schedule) using the Cloud Run Jobs `:run` API, a dedicated scheduler service account with job-invocation permission, OAuth authentication, UTC timezone and a daily cron such as `0 2 * * *`. Cloud Scheduler does not read `CRON_SECRET`; the Cloud Run job receives it from Secret Manager. Confirm the trigger fires after registration and alert on final job failure.

For every provider, verify the scheduled run's exit code, inspect `scanned`, `deleted`, `skipped`, `failed` and `batches`, and confirm no secret or private file metadata appears in logs. Alert on failed or missing runs. A zero-count result proves the route was reached and the catalog had no eligible rows at that moment; it does not exercise object deletion. In a disposable environment, create an eligible stale reservation and check that a scheduled run removes its object and releases quota. Do not treat an offline generated job or a healthy app as hosted cleanup acceptance.
