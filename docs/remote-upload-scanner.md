# Remote upload scanner contract

`UPLOAD_SCANNER_PROVIDER=remote` lets a distributed Node or Vercel host send an upload to an **operator-deployed** scanner over HTTPS. Set server-only `UPLOAD_SCANNER_URL` to its exact scan endpoint and `UPLOAD_SCANNER_TOKEN` to a unique random bearer secret of 32–512 non-whitespace characters. The URL cannot contain credentials, query or fragment, or point to localhost. Do not put either value in browser code, a public environment variable or a log. This repository supplies a small [reference gateway](../deploy/upload-scanner-gateway.mjs), its [Dockerfile](../deploy/upload-scanner-gateway.Dockerfile), client and protocol tests, but no hosted scanner service or malware-detection guarantee.

The endpoint must require `Authorization: Bearer TOKEN` on both methods:

| Request | Required response |
| --- | --- |
| `GET` | HTTP 200, `application/json`, exactly `{"status":"ready"}` when the scanner can accept work |
| `POST` with `application/octet-stream`, at most 5 MiB, and `X-Content-SHA256` | HTTP 200, `application/json`, exactly `{"verdict":"clean","sha256":"..."}` or `{"verdict":"infected","sha256":"..."}`; the digest is the scanner's own SHA-256 of the complete received bytes |

Each JSON response must fit within 256 bytes. The application refuses redirects, malformed or oversized responses, non-200 status, missing/unknown verdicts and a digest that differs from the bytes sent. It times out a scan after 20 seconds and a health probe after 1.5 seconds. Failed, missing or infected scans release no download bytes; failed intake scans leave no accepted object. A scanner must compare its own digest to the request header, scan the **entire** body before returning `clean`, and return a non-200 error when it cannot reach a trustworthy verdict. Never cache a clean verdict across requests or reply from an earlier request. Apply TLS, network access controls, secret rotation, service-level rate and concurrency limits, signature updates, and retention/logging policy at the scanner deployment.

The reference gateway listens on plain HTTP port 8081 inside a private container network, accepts at most four concurrent scans and talks to ClamAV over a private Unix socket. Build it with `docker build -f deploy/upload-scanner-gateway.Dockerfile -t jumpstart-upload-scanner:local .`. Configure `SCANNER_GATEWAY_TOKEN` to match the application's `UPLOAD_SCANNER_TOKEN`, `CLAMD_SOCKET` to the mounted socket path, and `PORT` if the private port differs. Run a ClamAV daemon and signature updater separately, mount only their socket into the gateway, and put the gateway behind an HTTPS terminator that forwards only `/v1/scan`; **never expose port 8081 directly to the internet**. The gateway has no browser interface, object-store credentials or persistent upload copy. The unit contract uses a fake daemon. The separate container rehearsal below exercises a real ClamAV engine and a local TLS edge; a production scanner deployment still needs acceptance.

Set `UPLOAD_DOWNLOAD_POLICY=scan-on-read` only after the endpoint passes `npm run check:upload-scanner` with clean and EICAR controls. The `/api/health/upload-scanner` route uses the authenticated `GET` and caches its liveness result for five seconds per app process; `ready` is not a signature test. The Vercel managed preflight accepts this policy only with Supabase upload storage and a complete remote scanner configuration. The actual scanner endpoint, credentials, routing, signature freshness and hosted behavior still require deployment acceptance. Every owner download rechecks object integrity and obtains a fresh verdict; this does not create a durable clean catalog state, make Eve attachments available, or erase derived copies.

## Reproducible scanner stack

[compose.upload-scanner.yaml](../compose.upload-scanner.yaml) packages a separate ClamAV service, the gateway and a Caddy HTTPS edge. Its ClamAV 1.4.6 image is pinned by digest and **requires AMD64**. On ARM, Docker must provide AMD64 emulation and Buildx; this is not a native ARM scanner image. The pinned Node and Caddy images support both architectures. The ClamAV daemon uses its full bundled signature databases, a persistent signature volume and the official FreshClam updater. Review and refresh image pins as part of your release process; a pinned image does not freeze signature updates.

The daemon has no TCP listener. Only the gateway mounts its socket volume; the gateway stays non-root, joins the pinned ClamAV image's socket group, has a read-only root filesystem and no published port. Caddy publishes HTTPS; the gateway's container network is internal, while ClamAV has a separate network for signature updates. Engine resource limits report an alert rather than a clean result. The socket group ID is tied to the pinned image and must be checked if you replace it. Reserve 4 GiB for ClamAV plus memory for the edge and gateway; see the [official container guidance](https://docs.clamav.net/manual/Installing/Docker.html).

Create a private, untracked `.env.scanner` file with `SCANNER_DOMAIN` set to the scanner's DNS hostname and `SCANNER_GATEWAY_TOKEN` supplied by your secret manager. For a directly reachable public HTTPS edge, set `SCANNER_BIND_HOST=0.0.0.0` and `SCANNER_HTTPS_PORT=443`, point DNS to that host and permit inbound TCP 443 so Caddy can obtain and renew its certificate. The default published address is loopback port 8443; it is not reachable from Vercel. Do not put a scheme, path or credentials in `SCANNER_DOMAIN`.

```sh
docker compose --env-file .env.scanner -f compose.upload-scanner.yaml up --build --wait --wait-timeout 240 -d
```

Set the application's `UPLOAD_SCANNER_URL` to `https://YOUR_SCANNER_DOMAIN/v1/scan` and its server-only `UPLOAD_SCANNER_TOKEN` to the same secret. Run the live scanner preflight from the application host before enabling scan-on-read. Monitor the updater, engine readiness, clean/EICAR controls and signature freshness separately. The HTTPS edge is independent of the app, so the same endpoint can serve Vercel + Supabase or a self-hosted Node deployment. Private gateway and socket ports must stay unpublished. The Compose recipe does not install a cloud service, acquire a hosted app identity or certify public certificate renewal.

Run `npm run test:upload-scanner:compose` with Docker Compose, Buildx, OpenSSL and an available AMD64 runtime. The test builds the **same** three images and overrides only the TLS certificate/listen address and the FreshClam background updater. It uses bundled full signatures for reproducible clean/EICAR controls, not a fabricated test-only virus database. It generates a temporary certificate, trusts it only in a child client process through `NODE_EXTRA_CA_CERTS`, and checks that the live endpoint fails certificate verification without that trust. TLS verification is never disabled. It also checks anonymous/wrong-token denial, digest mismatch, oversized bodies, unpublished daemon/gateway ports, the non-root gateway and fail-closed scan/readiness after stopping ClamAV. It removes its isolated containers, volumes, token and certificate files after the run. This rehearsal does not exercise a public CA, FreshClam's live CDN or hosted Supabase/Vercel routing.
