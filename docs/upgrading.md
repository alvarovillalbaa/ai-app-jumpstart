# Upgrading a template-based application

A repository created from this template has its own history and may have changed the UI, agent, data model and deployment settings. Treat a newer template revision as a source of reviewed changes, not as a branch to merge blindly. Record the current application commit, template source commit or release tag, application data provider, Workflow world, image digests and applied migration versions before starting. Until a release tag exists, use the exact template commit SHA.

## Prepare a candidate

1. Create an upgrade branch in the application's repository. Keep a separate checkout of the old and new template revisions so you can compare their files and release notes without overwriting local work. Copy only reviewed changes into the application. Preserve its identity, secrets, Auth redirects, custom tools, UI components and deployment manifests. Regenerate AI Elements/shadcn components only in the branch and review their diffs.
2. Use the Node 24 version in `.nvmrc` and run `npm ci` against the candidate lockfile. Review dependency and runtime changes, including the installed `node_modules/next/dist/docs/` guides and `node_modules/eve/docs/README.md` when changing their code. Do not edit an already applied SQL migration; add a new ordered file. Keep Convex functions and generated Supabase types aligned with their schema source.
3. Run `npm run check`, `npm run check:docs`, `npm run test:ai` and the [integration suites](testing.md) for every affected provider and surface. Build the target artifact with `npm run build:local`, `npm run test:vercel-build` or the [Amplify path](amplify-self-managed.md) as appropriate. Rehearse a fresh install and startup from the candidate commit; uncommitted files and local caches are not release evidence.

## Prepare data and runtime changes

For PostgreSQL or Supabase application data, use the target environment's private migration connection to run `npm run db:migrate -- --dry-run`. Review the exact pending SQL and a restorable backup, rehearse the upgrade against a disposable database populated from the previous version, then apply migrations once in a serial release job. The dry run does not execute SQL. Migrations should be additive while old and new application instances can overlap; code rollback does not reverse a database migration. For Convex, review and deploy compatible functions/schema for the selected deployment before rolling out code that requires them. SQLite upgrades need a stopped-service [snapshot and restore rehearsal](local-recovery.md) before starting the new image.

Eve Workflow storage is separate from application data. If changing the Workflow backend or package, follow [Workflow storage](workflow-storage.md) and apply its migration separately from application SQL. Keep the compiled Workflow provider marker, runtime selector and database URL together. A running job may hold a lock across replacement; verify its recovery instead of assuming a healthy new process resumed it. If local private uploads are enabled, preserve their volume with the matching application and Workflow recovery set. For separate PostgreSQL stores, use the [two-database recovery procedure](postgres-recovery.md).

## Roll out and verify

Use one deployment owner and one environment at a time: staging first, then production after acceptance. For a self-hosted Docker stack, build from the reviewed commit, retain the application and ingress image identities, keep its data volumes, and use the selected [Compose overlays](hosting.md#self-hosted-node--docker). For AWS/Azure/GCP containers, build and pin both image digests, validate the filled provider manifest, run the [one-off migration jobs](cloud-migrations.md), then update the runtime. For the maintained Vercel + Supabase path, run `npm run check:managed-config`, validate the Vercel build and deploy through the documented [Eve integration](hosting.md#maintainer-managed-vercel--supabase). The [self-managed Amplify recipe](amplify-self-managed.md) has a separate web adapter and long-running Eve worker; do not substitute the managed SSR path without its acceptance gate.

After rollout, verify public web/data/Eve readiness and run the two-owner [post-deployment smoke](hosting.md#post-deployment-data-smoke). When chat is enabled, include one budgeted owned turn, reload, cross-owner denial and a distinct-chunk streaming check through the real ingress. If uploads are enabled, verify private object storage, the scanner/release policy and scheduled cleanup. Replace one instance and check a completed conversation plus a new turn. Record the deployed revision, image digests, migration ledger and smoke results for each environment.

If acceptance fails, stop traffic to the candidate and redeploy the previous compatible artifact. Do not automatically reverse additive migrations or restore a backup over new writes. A database restore is a separate recovery decision requiring a stopped writer set and a verified matching snapshot. Keep the draft release record and failure evidence so the next candidate can be checked against the same boundary. See [operations](operations.md) for backups, budgets and unresolved starts.
