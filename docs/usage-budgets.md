# Usage budgets

`lib/budgets/` implements a server-only reservation ledger across SQLite, PostgreSQL, Supabase PostgREST and Convex. `BudgetedCreation` composes it with the conversation broker. The production receipt hook enforces runtime admission and settlement for account-owned turns and compaction. [Account chat](account-chat.md) wires browser/API creation and exposes owner-only usage snapshots through `/usage`, REST, CLI and MCP. It is disabled by default. Enabled account chat requires an attributed price-and-token cost basis and rejects reservations below its calculated quote; provider output limits are applied before each AI SDK invocation. Actual prices, input-token enforcement, paid-provider acceptance and reconciliation of outstanding/disputed starts still require review.

## Admission

The server supplies an immutable operation ID and request hash, an estimated maximum cost, a policy ID, a daily limit, an active-run limit and a rolling one-minute request limit. Amounts are integer micro-USD: 1,000,000 units represent one US dollar. Browser request bodies contain only the message and operation ID; they cannot set prices, limits or usage.

Reservation checks and writes are atomic. Identical retries return the original reservation without charging again. A different owner, request hash, quote or policy ID cannot reuse it. The account runtime derives its ledger policy ID as `runtime-v3:<sha256>` from the entire canonical reviewed envelope: configured policy label and limits, estimate, call cap, SDK input-payload bound, model allowlist, pricing provenance, token bounds and prices. Reordering models leaves the ID unchanged. Changing any bound or price creates a different envelope, so a lost checkpoint cannot silently readmit the same operation under wider settings. Quota failures occur before dispatch. Provider errors and invalid estimates also fail closed. The creation wrapper reserves capacity before calling the durable conversation coordinator, so a retry can recover a crash between budget admission and conversation reservation without charging twice.

`now` is a trusted server clock input, not client data. Day boundaries use UTC. Hosts should have synchronized clocks. Active reservations remain active across midnight; their eventual charge belongs to the admission day. The rolling request count includes accepted requests after they settle, so finishing quickly cannot bypass the rate limit.

## Settlement and uncertainty

Only trusted server code may settle a reservation after observing the execution outcome. Known cost replaces the estimate, even if it exceeds it. An overage remains visible and can block later work; the ledger never clips reported usage to the quote. A verified zero cost is explicit `0`. Unknown cost is `null`: it charges the estimate conservatively and increments `unknownCosts`.

Identical settlement retries are idempotent. A conflicting later settlement is rejected, preventing duplicate refunds or silent history rewrites. An operator can correct an **already-settled** amount through the backend-only [reconciliation command](operations.md#correct-an-already-settled-cost). The operation compares the exact previous cost (including `unknown`), updates the charged total atomically and appends an immutable actor/reason/evidence audit row. The correction ID makes a lost-response retry idempotent. It does not reconcile a reservation that is still outstanding.

Timeouts, dropped responses, revocation and elapsed time alone do not refund capacity. A runtime may already have accepted work. There is no automatic expiration of outstanding reservations. An authenticated owner may explicitly cancel a `starting` conversation before runtime binding; that atomic transition prevents a later model call and settles the reservation at verified zero. A budget-only reservation is first fenced by a matching conversation tombstone, so a delayed broker cannot dispatch it. An active binding wins the race and cannot be refunded this way. A failed budget write after successful revocation leaves capacity reserved until idempotent retry or operator reconciliation. Disputed starts and settlements still need operator investigation; the creation broker never blindly redispatches them.

The daily admission limit bounds recorded usage plus reserved estimates. It is not a guarantee about a provider invoice. Estimation must account for the allowed model, context size, output limits, tool calls and runtime retries. Pricing provenance, runtime cost collection and complete per-turn integration are still required before enabling production chat. Missing provider prices must remain unknown.

## Persistence and access

SQLite uses an immediate transaction and a persistent WAL database. PostgreSQL serializes mutations on an owner account row; a single database function performs the admission or settlement transaction. Supabase calls the same function through PostgREST. It uses [`SECURITY INVOKER`](https://supabase.com/docs/guides/database/functions), an empty search path, RLS and explicit grants. Browser `anon` and `authenticated` roles cannot read/write ledger tables or execute the function. Runtime backend credentials stay private.

Convex uses serializable internal mutations and per-owner/day aggregates. Its authenticated backend HTTP action is the only network entrypoint. It does not scan an entire history to calculate daily usage. No browser-facing ledger mutation or refund endpoint exists.

The operator-only `npm run starts:inspect -- list` command pages outstanding reservations across all owners and joins each page with current conversation state and model-attempt counts. It uses backend database credentials directly and has no public REST or MCP route. See [operations](operations.md) for pagination and interpretation. SQL providers index reserved rows by creation time and operation ID; Convex uses the equivalent index. The inventory is read-only and nontransactional. `npm run budgets:reconcile -- show` displays one owner's reservation and its latest 100 correction entries; `correct` requires an explicit `--apply` to mutate a settled amount. The full audit log stays in the application database.

The read-only `/usage` screen calls `GET /api/v1/usage` with the current registered user's bearer token. CLI `npm run app -- usage`, MCP `usage_get` and the `usage:///current` resource use the same owner-scoped view. It shows the UTC day, charged and reserved micro-USD, daily limit, active reservations, requests in the last minute and unknown-cost settlements. The screen clears prior values on account change or a failed refresh. Record API keys cannot access this account budget view. Its dollar rendering keeps six decimal places so small test and development amounts remain visible; it is an application ledger, not a provider invoice. With Supabase sign-in and the application store configured, these reads remain available when `AI_CHAT_ENABLED=false`, independently of model credentials, signing keys, a budget policy and Eve. The current view then returns `dailyLimitMicros: null` and the screen shows that chat is disabled without a spending progress bar. Null means no active allowance; it does not cancel reservations, erase charges or authorize unlimited credit. An enabled but malformed chat configuration still fails the current view rather than pretending chat is disabled.

`GET /api/v1/usage/reservations?limit=50&cursor=...`, CLI `npm run app -- usage reservations [--limit N] [--cursor CURSOR]`, and MCP `usage_reservations` page the verified owner's historical reservation rows, including admission time, policy ID, estimate, current status and nullable actual cost. A settled row with `actualMicros: null` has an unknown cost and charges its estimate in the daily view. The timestamp/operation cursor handles multiple reservations admitted in the same millisecond. The read never exposes request hashes or other owners' entries.

`GET /api/v1/usage/corrections?limit=50&cursor=...`, CLI `npm run app -- usage corrections [--limit N] [--cursor CURSOR]`, and MCP `usage_corrections` page the same owner's cost corrections across operations, without the operator actor, reason or evidence reference. The timestamp/correction-ID cursor avoids silently truncating an operation after 100 corrections, unlike the separate operator preview command. REST ledger history needs only verified account authority and the application store, including when the runtime configuration is unavailable. MCP retains usage tools while chat is disabled; enabled MCP still validates its runtime configuration. Both account history views are live paged reads, so concurrent changes may appear or be missed. The [application-visible export](data-access.md#export-visible-application-data) includes these selected rows; model-attempt IDs, operator correction notes/evidence and historical daily aggregates still require separate export coverage.

Before upgrading an enabled runtime, inspect outstanding work. Earlier ledger policy IDs, including `runtime-v2`, conflict with the new fingerprint. Restored turns lacking output-cap or input-payload snapshots refuse another provider request. Pending owner cancellation remains available; active or ambiguous work needs operator evidence and reconciliation. Do not delete reservations or attempt tombstones to force a replay.

Apply SQL migrations with `npm run db:migrate`; Convex deploys its schema and functions normally. Keep ledger history when restoring data: restoring only application conversations can erase reservations and permit duplicate admission.

## Runtime enforcement

`agent/hooks/session-access.ts` uses `RuntimeBudgets` and Eve's durable `defineState` context. The first turn uses its signed creation operation; later turns derive a stable operation ID from the owner, session and runtime turn ID. The hook admits trusted owner/session/model context; AI SDK middleware then rechecks ownership and claims a durable attempt immediately before each provider invocation. A fresh nonce prevents restored event context from reusing a spent attempt. Actual AI SDK retries within a single step, as well as re-emitted Eve steps, consume additional attempts; claims after settlement or past the cap fail. The durable turn snapshots its call, output and input-payload caps. Requests use the lower of the admitted and current `maxOutputTokens`, including streamed responses and compaction, while preserving tighter limits set by the caller. Increasing deployment caps cannot widen a restored envelope. An envelope change during re-admission fails with a policy conflict and retains its reservation.

`maxInputBytes` bounds the UTF-8 JSON size of the SDK content envelope: the full prompt (including system instructions and prior tool results), tools and schemas, tool choice, response format, provider options and stop sequences. It defaults to 262,144 bytes and can be configured from 1 to 1,048,576. The counter includes JSON escaping and Unicode, stops on overflow without serializing a copy, and refuses cyclic, opaque, accessor-bearing or excessively nested content. Every request, retry and compaction is checked before claiming a provider attempt. A tighter current bound applies immediately; a restored bound cannot be widened. No text is truncated or logged. If the durable attempt count is zero, denial releases the reservation at verified zero model cost; an already-claimed or ambiguous attempt retains conservative settlement.

This byte count is not a token count, the provider's wire representation, or the size of content fetched through a remote reference. Provider-added formatting, stateful references and media need their own accounting. [OpenAI's input-token counting API](https://developers.openai.com/api/docs/guides/token-counting) counts the provider-specific request, including roles and tools; the Gateway/Eve payload is a different boundary. Exact token admission for the selected routing path remains open.

The hook installs the middleware through the AI SDK's public default-provider configuration, preserving the root agent's string model ID and Gateway routing. An existing default provider is wrapped rather than replaced. Keep this installation when extending account-owned agents; direct model objects bypass string resolution and need `modelWithBudget` explicitly. See [AI SDK provider management](https://ai-sdk.dev/docs/ai-sdk-core/provider-management#global-provider-configuration) and [middleware](https://ai-sdk.dev/docs/ai-sdk-core/middleware).

Automatic compaction consumes a call from the active turn's envelope. Manual compaction gets its own reservation. Eve's compaction completion does not report cost, so it settles conservatively as unknown. Completion, failure and cancellation settle a turn when sufficient evidence is available. Attempts missing from restored workflow usage totals prevent a refund: the ledger count is compared with completed usage reports. Partial overages with missing costs, or costs outside the ledger's supported range, remain reserved for explicit reconciliation.

Configure `AI_BUDGET_POLICY_JSON` privately with these fields:

| Field | Meaning |
| --- | --- |
| `policy.id` | Version of the reviewed cost policy |
| `policy.dailyMicros` | Daily recorded-plus-reserved allowance |
| `policy.maxActive` | Maximum outstanding operations across days |
| `policy.maxPerMinute` | Accepted operations in a rolling minute |
| `estimateMicros` | Reviewed maximum envelope for one turn or manual compaction |
| `maxModelCalls` | Maximum provider attempts, including retries and automatic compaction |
| `maxInputBytes` | Optional SDK content-envelope bound in UTF-8 JSON bytes; defaults to 262144, maximum 1048576; not a token count |
| `modelIds` | Exact runtime model IDs covered by the envelope |
| `costBasis.sourceUrl` / `reviewedAt` | HTTPS pricing source and date of operator review |
| `costBasis.models` | Exactly one entry per allowed model ID, with `maxInputTokens`, `maxOutputTokens`, `inputMicrosPerMillion` and `outputMicrosPerMillion` |
| `costBasis.maxOtherMicros` | Additional allowance for paid tools or other costs not included in model-token prices |

Any enabled account chat requires `costBasis`. The validator rounds each model's input and output quote up to whole micro-USD, takes the most expensive allowed model, multiplies it by `maxModelCalls`, adds `maxOtherMicros`, and rejects `estimateMicros` below that result or above the daily allowance. It uses integer arithmetic even when intermediate products exceed JavaScript's safe integer range. The same parse runs in Next's account-chat configuration and Eve's runtime; the managed-host preflight exercises it without making a provider call. Test fixtures use attributed synthetic prices.

Run `npm run check:budget-policy` with the private policy in `.env.local` before a release. It prints the configured policy label, derived ledger envelope ID, calculated micro-USD quote, reservation, SDK input byte limit, model IDs, review date and pricing-source host, or field names that need correction. It makes no provider call and prints no policy JSON or keys. This preflight and the managed-chat preflight reject reviews more than 30 UTC calendar days old or dated in the future. The live runtime does not expire an already deployed review. Update the policy ID, source and review date whenever prices or token assumptions change; check the actual current prices and rehearse the production model separately. A recent date alone does not verify the quoted prices.

There is no default price or allowance. Use current provider and routing prices for the exact model ID and document the reviewed token assumptions. **`maxInputTokens` remains an operator assumption; `maxOutputTokens` is applied to provider request parameters by the runtime middleware, not by the quote validator.** Eve's session token limits are checked after a call and permit a user continuation; they cannot turn this arithmetic check into a hard invoice ceiling. Input growth, provider-internal retries outside AI SDK middleware, changing prices and paid tools can exceed a reservation; unknown or higher actual cost remains visible and may require reconciliation. Review the model's actual context/output limits and production-model behavior before enabling paid chat. The root agent disables Eve's default tool set and exposes the authored tools; its model selection remains unchanged. Paid tools or additional agents need their own cost admission before being enabled. Development sessions using Eve's local authenticator do not enter this application-owned budget path.

## Verification and remaining work

The shared `budgetContract` runs on all four providers. It exercises concurrency, idempotency, owner-isolated reservation lookup, bounded cross-owner inventory pagination, daily and active limits, the rolling minute boundary, settlement, audited correction, unknown costs, overages, midnight behavior and durable attempt caps. SQLite also tests independent connections, reopening persisted data and the operator CLI. Supabase tests direct table and RPC denial with real database roles. Creation tests cover dispatch denial, ambiguous acceptance, a crash between budget and conversation writes, delayed-dispatch fencing during budget-only cancellation, and provider failure.

The real compiled Eve fixture exercises the same production string model configuration through a fixture-only default provider, records every requested output cap, and proves oversize input fails before provider entry with zero attempts and zero model cost. It also verifies owned follow-ups, manual compaction settlement, daily-limit denial, tool-loop call caps and a queued forged approval that does not produce another model call or enlarge the budget. It uses a fresh temporary app/queue namespace and the actual production hook. The account browser contract checks the usage screen and REST/CLI/MCP parity with a real authenticated user after quota exhaustion, then checks another account sees zero. It also proves budget-only cancellation in a disposable ledger. Cost-basis tests cover exact model coverage, round-up arithmetic, underquotes, missing reviews, overflow and canonical envelope fingerprints. Provider-boundary tests exercise real AI SDK retry and streaming behavior, restored/lowered caps, wholly lost first-step checkpoints, model mismatch, legacy envelopes and revocation before networking. Input tests compare UTF-8/escaped JSON sizes with the actual encoder, exercise tool-result/schema growth, shared references and early overflow, and deny cycles, accessors, opaque objects and excessive nesting. The mock provider records request parameters; it does not prove a vendor accepts or obeys those limits. Remaining work includes populating and verifying actual provider prices/token assumptions, disputed-start reconciliation beyond owner cancellation and deployed acceptance. These local checks do not certify every optional tool, agent, callback or provider configuration.
